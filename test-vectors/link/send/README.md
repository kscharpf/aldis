# Sending-side link engine scenarios

Engine scenarios for the sending engines of [docs/04-engines.md](../../../docs/04-engines.md) §2 and §4 (M4 WP-2a): PacketGenerator, AccessGenerator, BitstreamGenerator, ChannelMux with its multiplexing policies, and MapSegmenter. Many scenarios per file, in the format of [07 §3](../../../docs/07-test-vectors.md) and `schema/engine-scenario.schema.json`. They are generated by the independent model [`../../models/link_send.py`](../../models/link_send.py) (TV-023), which was written blind: from the Blue Books and `docs/` only, by an agent that had not read any implementation (there is none yet for the link engines) and none of the Rust, C, or C++ sources. `python3 -I test-vectors/models/link_send.py --check test-vectors/link/send/*.json` replays every scenario and compares each file with what the generator writes.

**The JSON is never edited by hand.** `link_send.py --write` writes every file here in a fixed order and format; change the model, then regenerate. A file that is not released yet changes by regeneration; a released file only by new cases and `superseded` marks (TV-021).

The files are awaiting their runner (`AWAITING_RUNNER` in `xtask/src/consistency.rs`, as `cop1/scenarios/` was): the engines are WP-3 (PacketGenerator), WP-4 (ChannelMux, Access and Bitstream generators), and WP-6 (MapSegmenter), and each of them removes its files from the exemption when its host test runs them. Until then the files are no evidence for `cargo xtask trace`.

Scenario ids are `link-send-<engine>-<protocol>-lnk-<nnn>-<topic>` (engine: `pg` PacketGenerator, `ag` AccessGenerator, `bg` BitstreamGenerator, `mux` ChannelMux, `seg` MapSegmenter), named for the main row they exercise; the `requirements` of each scenario name every row it exercises.

## Conventions

Those of [cop1/README.md](../../cop1/README.md): `at_us` is absolute and never decreases (two steps may share an instant); a step lists the complete, ordered outputs of its input (TV-010, TV-012); an input the engine refuses is `{"error": "<kind>", "field": "<name>"}` as the only output (`field` is the name of the catalogue of [04 §5](../../../docs/04-engines.md); the state is unchanged, API-058); octets are upper-case hex strings, keys end in `_hex`; `null` is not a value anywhere in a step. A step of `packet-generator` and `map-segmenter` asserts the deadline after it, `expect_timeout_us` or `expect_no_timeout: true` (API-053); the other engines have no timer and assert none. No step asserts `expect_state`: the states are implementation-defined.

The input and output vocabulary is the model's; 04 names the kinds (`Release`, `Offer`, `Opportunity`, `NextFdu`, `Timeout`, `Reconfigure`, `Submit…`, `SetOcf`, `SetFsh`, `SetInsert`; the actions `DataField`, `Transmit`, `Fdu`, `Notify`) and not their fields, so the field names below are what the runners of WP-3, WP-4, and WP-6 map their inputs to.

An engine instance serves one VC (one MAP for a USLP packet generator), so its inputs name no VC; the multiplexer's do.

### Configuration

Each file gives the engine's `config` once; a scenario that needs another gives its own. The keys are the managed parameters the engines use (the parameter names are the model's):

* **packet-generator**: `protocol` (`tm`, `aos`, `uslp`), `aos_issue` (5, or 4), `vc`, `field_len` (the octets of the `data_field`, header included), `valid_pvns` (`0` Space Packet, `7` Encapsulation Packet), `max_packet_len`, `queue_capacity` (octets), `release_deadline_us` (absent: release only when full), `idle_policy` (`oid`, `idle_field`), `idle_packet_kind` (`space_packet`, `encapsulation`; TM and AOS), `idle_pattern_hex`, and for USLP `upid`, `map_id`, `qos`.
* **access-generator**: `protocol`, `vc`, `field_len`, and for USLP `upid`, `map_id`, `qos`, `max_sdu_len`, `idle_pattern_hex`.
* **bitstream-generator**: `protocol` (`aos`), `vc`, `field_len` (the B_PDU), `idle_pattern_hex` (`00` or `FF`).
* **channel-mux**: `protocol`, `scid`, `frame_len`, `fecf`, `policy.kind` (`fixed_priority`, `round_robin`, `weighted_round_robin`), `vcs` (each: `vcid`, `role`, `priority`, `weight`, `ocf_init_hex` (present: the VC has a VC_OCF), `fsh_init_hex` (TM), `sec_header_len`, `sec_trailer_len`; USLP also `map_id`, `qos`, `vcf_len_sc`, `vcf_len_exp`), TM: `oid_vc` (the dedicated VC, which is one of `vcs`), `mc_ocf_init_hex`, `mc_fsh_init_hex`; AOS: `fhec`, `cycle_in_use`; AOS and USLP: `insert_zone_len`, `insert_init_hex`; USLP: `source_or_destination`, `oid` (`qos`, `vcf_len`, `ocf_init_hex`). The data field a VC gives the multiplexer is the frame length minus the other fields of its frame; the model computes it and the scenarios offer exactly that many octets.
* **map-segmenter**: `protocol` (`tc`, `uslp`); TC: `segment_header`, `fecf`, `max_fdu_len` (Segment Header included), `blocking` (VC without a Segment Header), `maps` (`map_id`, `segmentation`, `blocking`, `max_sdu_len`); USLP: `max_tfdf_len` (TFDF Header included), `maps` (`map_id`, `service`, `upid`, `blocking`, `max_sdu_len`, `release_deadline_us`).

## Readings the model makes

Each is either settled by a Blue Book clause or a resolved open issue, or a judgement within what 04 leaves open. The ones marked **J** are in the report of the work package for the maintainer's review; none of the cases below depends on a reading the maintainer has not been told.

1. **Where octets are written (LNK-012).** A generator writes the octets of an accepted packet into the field being assembled at once, as far as they go; the field is started when its first octet is written, at the `at_us` of that input; it is releasable when full or when `Timeout` has marked it. A packet that does not fit goes on in the next field, which is started by the `Release` that returned the full one. The queue holds only the octets of packets that did not fit the field yet. **J**
2. **A releasable field takes no more octets.** The scenarios never submit a packet between the `Timeout` that marked a field and the `Release` that returns it. **J**
3. **Space Packet Idle Packet fields.** APID `0x7FF`, Secondary Header Flag 0 (133.0 §4.1.3.3.3.4), Sequence Flags `11`, count 0, Packet Type 0 (133.0 states no type for an Idle Packet; the project's idle builder, space-packet.md SPP-010, states the rest), data = the idle pattern from its first octet. A remainder below 7: the 7-octet idle packet is begun, its last 7 − r octets are the first octets of the next field and make that field started at the `Release` (LNK-013). The field that holds an idle packet start has its FHP at that start: a packet start is a packet start whether the packet is idle or not (the Blue Books keep "Idle Packet" and "Idle Data" apart, 132.0 §4.1.4.6.3 note 4, 732.0 §4.1.4.2.3.4 note 4). **J**
4. **Encapsulation Idle Packets.** One octet `E0`; 2 to 255 octets `E1` and the total; 256 to 65 535 octets `E2 00` and the 2-octet total (133.1 Table 4-2); the data = the idle pattern.
5. **IdleField policy.** `Release` with a releasable field returns it; with none it returns the idle field and does not touch a partly filled field. The scenarios do not combine an idle field and a partly filled one. **J**
6. **Multiplexing policies.** Round robin and weighted round robin walk the VCs of the configuration in ascending VCID order, the dedicated TM idle VC included; the first selection after start-up is the lowest VCID (round robin) or the first VC with its full weight (weighted round robin). A VC with no field forfeits the rest of its turn when the walk reaches it. No scenario has an OID frame while a weighted turn is part used. **J**
7. **Counts.** Assigned at selection; TM: MC count on every frame, VC count on every frame of the VC, the OID frame included; AOS: the VC count of VCID 63 is kept like any VC's; USLP: one count per VC and QoS, with the Count Length of the QoS, wrapping modulo 2^(8 n). Reconfigure keeps the OID generator and the frame counts (132.0 §4.1.2.5.3, §4.1.2.6.3, §4.1.4.6.2.1: no reset unless unavoidable; CMN-021, LNK-036). **J** for the counts
8. **OID frame details.** TM: Synchronization Flag 0, Packet Order Flag 0, Segment Length ID `11`, FHP `0x7FE`, OCF and Secondary Header as the VC's (or the MC's); AOS: Replay Flag 0, the OID frame has no OCF; USLP: Bypass/Sequence Control Flag by `oid.qos` (the Blue Books state none for an OID frame), Protocol Control Command Flag 0, TFDF Header rule `001`, UPID `31` (Only Idle Data), pointer at the last TFDZ octet, TFDZ from the OID generator.
9. **Insert Zone.** The slot's current value is inserted in every frame; a frame sent with no `set_insert` since the previous frame repeats it and the action is followed by `Notify(InsertSduRepeated)` (OI-68). Every scenario with an Insert Zone calls `set_insert` before its first `opportunity`. **J**
10. **Segmenter order.** The segmenter finishes the SDU in progress before it starts the next queued SDU, whatever its MAP (LNK-041); queued SDUs are started in the order of submission (232.0 §4.3.3.3 leaves the order of MAPs to the project). Where blocking is permitted, `next_fdu` packs the complete packets that follow each other in the queue, of the same MAP, as long as they fit, and a packet that needs segmentation is not packed. **J**
11. **Octet stream.** The TFDZ of rule `011` holds up to `max_tfdf_len − 1` octets in the order submitted; a TFDZ that is not full is returned with the octets it holds. A scenario has either an octet-stream MAP or SDU MAPs with queued data, never both pending at once.
12. **Reconfigure.** `Discarded.octets` is the number of user octets the engine held: those of the field being assembled and of the queue (an idle residue included), an SDU's octets not yet sent, the offered fields of the multiplexer; bits are counted in whole octets and the scenarios use whole octets. **J**

## Not covered

Cases the Blue Books or 04 do not settle, with no scenario until the maintainer decides: the Packet Order Flag, Segment Length ID, and FHP of a TM frame with Synchronization Flag 1 (a TM VCA frame through the multiplexer); the AOS VC Frame Count and cycle wrap (the model has no way to preset a count, and 2^24 frames are too many to script); the sequence-controlled VCF Count of a USLP VC in which COP-1 is in effect (FOP-1 supplies it; how it reaches the multiplexer is not in 04); the Insert Zone of the first frame when no `set_insert` came; a weighted turn part used at an OID frame; the IdleField policy with a partly filled field; an SDU of the wrong length on TM/AOS VC Access (no field name for the error in 04 §5); a change of QoS in the middle of a segmented SDU; the selection among several Master Channels (04 gives no configuration for them); the header and trailer sizes above the limits of API-071 and the other configuration errors (LNK-078, WP-3 to WP-6).
