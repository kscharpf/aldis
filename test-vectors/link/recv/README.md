# Link engines, receiving side: conformance scenarios

Engine scenarios for the three receiving engines of [04-engines.md](../../../docs/04-engines.md) §3: the **FrameReceiver**, the **PacketExtractor**, and the **MapReassembler** (LNK-050…054, LNK-060…064, LNK-070…072, LNK-077, LNK-079, and LNK-003 where a Reconfigure appears), in the format of [07 §3](../../../docs/07-test-vectors.md) and `schema/engine-scenario.schema.json`. They are generated by the independent model [`../../models/link_recv.py`](../../models/link_recv.py) (TV-023), which was written blind: from the Blue Books and `docs/`, by an agent that had not read any implementation (`crates/`, `exerciser/`, `fuzz/`, `crosscheck/`, `refapp/`, `include/`, the Rust source of `xtask/`). For format only it read the COP-1 model and scenario files. No engine of the receiving side existed when it was written.

**The JSON is never edited by hand.** `python3 -I test-vectors/models/link_recv.py --write` writes every file here in a fixed order and format; `--check test-vectors/link/recv/*.json` replays every scenario through the model and compares the file with what the generator writes. Change the model, then regenerate. (`cargo xtask vectors validate` runs `--check`; `cargo xtask vectors generated` knows only `test-vectors/cop1/` and does not yet regenerate this directory.)

## Conventions

As in [cop1/README.md](../../cop1/README.md): `at_us` is absolute and increasing; a step lists the **complete, ordered** outputs of its input (TV-010, TV-012); `expect_state` and the deadline fields are absent (the receiving engines have no state name and no timer); octets are upper-case hex strings, keys end in `_hex`; an input an engine refuses is `{"error": "<kind>"}` and changes nothing (no scenario here refuses an input, see "Cases the model refuses"). The `config` is given once per file and replaced for a scenario that needs another. A frame input is the complete frame (header, Insert Zone, data, OCF, FECF) that the caller has validated; the FECF in the scenarios is correct.

Outputs are in the order the procedure produces them (API-057): for a frame, MC gap, VC gap, FSH, Insert SDU, OCF, then the data field (04 §4); for a data field of the extractor, the outcome for the packet in progress, then the packets and the extraction errors in the order of their octets.

## Outputs

| Output | Meaning |
|---|---|
| `{"frame_discarded": {"reason", "vc", "map"?}}` | FrameDiscarded (LNK-050) with the reason of 04 §5: `UnknownChannel`. It is the only output for the frame |
| `{"notify": {"kind": "FrameGap", "scope": "mc" or "vc", "vc"?, "missing"}}` | LNK-051; `missing` = count − expected, modulo the range |
| `{"notify": {"kind": "LossFlag", "scope": "vc", "vc"}}`, `{"notify": {"kind": "LossFlag", "scope": "physical_channel"}}` | the answer to `frame_loss`: one per configured VC in configuration order, then one for the channel |
| `{"notify": {"kind": "Discarded", "octets"}}` | partial packet or SDUs discarded (LNK-061, LNK-003) |
| `{"deliver": {"kind": "DataField", "vc", "data_hex", "gap", "fhp"?, "bit_count"?, "replay"?}}` | the data field for the VC's extractor, reassembler, or VCA user: TM the data field and `fhp` (packets VCs); AOS the M_PDU, the data field, or the valid bits of a B_PDU (`bit_count` bits, left aligned, the unused bits of the last octet zero); USLP the TFDF. `gap` is true when a gap was detected since the last data field delivered for the VC (the flag stays set across frames that deliver none, 732.0 4.3.3.3 note). `replay` on AOS only (LNK-054) |
| `{"deliver": {"kind": "FshSdu", "scope", "vc"?, "data_hex"}}` | the whole Secondary Header, ID octet included (132.0 3.2.4 note: 2 to 64 octets); `scope` `vc` or `mc` by the configured service |
| `{"deliver": {"kind": "InsertSdu", "data_hex", "replay"?}}` | the Insert Zone (AOS, USLP) |
| `{"deliver": {"kind": "Ocf", "scope", "vc"?, "report", "ocf_hex", "replay"?}}` | the OCF; `report` is `Type1` (bit 0 = 0: a CLCW, or a PLCW on USLP) or `Type2` |
| `{"deliver": {"kind": "Packet", "pvn", "data_hex", "incomplete", "vc"?, "map"?}}` | an extracted packet (`vc`, `map` from the reassembler); `incomplete` is the Packet Quality Indicator |
| `{"deliver": {"kind": "Sdu", "vc", "map", "data_hex", "octet_stream"?}}` | a MAP_SDU; `octet_stream` true for a chunk of rule `011` |
| `{"extraction_error": {"kind"}}` | `PacketTooLong`, `InvalidPvn`, `LengthInconsistent` (04 §5) |
| `{"reassembly_event": {"kind", "vc", "map"}}` | `GapDiscard`, `SequenceViolation`, `UnknownMap` (04 §5) |
| `{"counter": {"name", "value"}}` | the answer to `query` |

Counters (LNK-002): one per FrameDiscarded reason, extraction error, and reassembly event, named as in 04 §5; `oid_frames`, `gaps` (gap actions raised), `idle_packets` (idle packets seen by the extractor). The names other than 04 §5's are the vocabulary of these files.

## Configuration

* **FrameReceiver:** `protocol`, `scid`, `frame_len`, `fecf`, `vcs` (`vcid`; TM and AOS `role` `packets`, `vca`, or `bitstream` (AOS only); AOS `ocf` (the VC has an OCF); USLP `maps` and `cop` (COP-1 in effect)); TM `ocf_service` and `fsh_service` (`vc`, `mc`, `none`); USLP `ocf_service`; AOS and USLP `insert_zone_len`; `accept_rejected_frame_insert_zone` (LNK-079, default off). VCID 63 of AOS and USLP is valid without an entry (732.0 Table 5-2 note; 732.1 Table 5-2 note 2).
* **PacketExtractor:** `protocol`, `valid_pvns`, `max_packet_len`, `deliver_incomplete`, `deliver_idle` (LNK-061, LNK-063).
* **MapReassembler:** `protocol`; TC `vc` and `maps`; USLP `maps` with `vc`; each map has `map` and `service` (`packets`, `sdu`, or `octet_stream`).

## Readings the model makes

Each is a reading the Blue Book or 04 settles, or a choice for something they leave to the implementation, made so that the vectors can state an exact output.

1. **Order of actions is the order of the procedure (API-057).** 04 §4 lists the extractor's errors after its deliveries; a `LengthInconsistent` found at the FHP is placed before the packets that start at the FHP (scenario `fhp-wins-over-length`).
2. **FHP wins (132.0 4.3.2.4, LNK-060).** A packet in progress that still needs octets when the FHP is reached is abandoned (Discarded, or delivered Incomplete) and `LengthInconsistent` is raised; a field with the "no packet starts" value after a packet that ended exactly at a field end raises `LengthInconsistent` and is skipped.
3. **Resynchronisation.** Start-up, a gap, and every extraction error leave the extractor out of synchronisation: octets are skipped without any event until a field with an FHP (a skipped field is not a Discarded octet count, only the partial packet is).
4. **A gap is sticky** until a data field is delivered for the VC (LNK-051, and 732.0 4.3.3.3 note for bitstreams).
5. **MC gap and VC gap are separate actions;** only a VC gap flags the data field.
6. **USLP:** VCF Count per QoS, tracked unless the count length is 0 or COP-1 is in effect on the VC (LNK-051); a gap in the reassembler discards the partial SDUs of the VC (`GapDiscard`), and a continuation that follows is a second event (`SequenceViolation`).
7. **Counts:** the first frame after start-up or Reconfigure sets the expectation; a count more than half the range ahead is not specified (below).

## Cases the model refuses

The model raises `Unspecified` for these, so none is in a vector. They are for the maintainer (see the report of the pull request).

* A frame count that goes backwards or repeats (LNK-051 "missing = count − expected, modulo" against CMN-031's "backwards or reset").
* `CrcMismatch`, `HeaderUncorrectable`, and `Security` discards: 04 §4 gives the engine no input that reports them, so they cannot be scenario steps.
* The `NotServed` reason, and the output for a TC frame that the receiver routes to FARM-1 (04 §4 says "one item" and §5 lists no Deliver kind for it).
* The Insert Zone of a frame for an unknown VC: 732.0 4.3.7.4 and 732.1 4.3.11.1.4 extract the IN_SDU "regardless of" the VC, while 04 LNK-050 and §4 return FrameDiscarded alone. The unknown-VC scenarios follow 04.
* USLP frames with the Protocol Control Command Flag set; a `raw_frame` while the option is off, of a wrong length, on AOS (replay metadata of an unvalidated header), or on USLP with a VCF Count Length other than 0 (the offset of the Insert Zone depends on it); what `frame_loss` does to the actions that follow (OI-68 says it sets the optional loss flags on them; 04 §4 lists only the Notify actions, so no frame follows a `frame_loss` in a scenario).
* Packets: an FHP beyond the zone; a packet that ends before the FHP, or inside a field that says no packet starts; a partial idle packet; a valid PVN other than 0 and 7; an Encapsulation length field of four octets, or a length shorter than the header; a gap flag on a field of only idle data.
* Reassembly: a complete SDU (flags `11`, rule `111`) while an SDU is in progress; a gap on TC or on an octet stream; two SDUs in progress on one USLP VC; a blocked FDU whose packets do not fit it; a Last Valid Octet Pointer beyond the zone; a rule on a MAP of another service; the maximum SDU size.
