# 04 — Engines (`aldis-link`)

`aldis-link` implements the **protocol procedures** of the data link standards (the "Protocol Procedures at the Sending/Receiving End" sections of 132.0, 232.0, 732.0, and 732.1) as sans-I/O engines following the contract in [03 §5](03-api-model.md#5-engines-the-sans-io-contract). COP-1 is specified separately in [standards/cop1.md](standards/cop1.md).

Engines are composable building blocks. A typical deployment instantiates one engine per VC (or MAP) plus one multiplexer per physical channel.

```
SENDING                                               RECEIVING
packets ─▶ PacketGenerator (per VC) ─┐                ┌─▶ FrameReceiver (per physical channel)
VCA SDUs ─▶ AccessGenerator (per VC) ─┼▶ ChannelMux ─▶ │     validate · FECF · demux · counters · OCF/FSH/IZ
B-stream ─▶ BitstreamGenerator (AOS) ┘   (per PC)     │   ├─▶ PacketExtractor (per VC)  ─▶ packets
OCF source, FSH source, IN_SDU ─────────▶             │   ├─▶ AccessReceiver (per VC)   ─▶ VCA SDUs
                                                      │   └─▶ MapReassembler (TC/USLP)  ─▶ packets / MAP SDUs
MAP SDUs/packets ─▶ MapSegmenter (TC/USLP) ─▶ FOP-1 / direct BD ─▶ frames
```

## 2. Sending side

The engines follow the step contract of [03 §5](03-api-model.md#5-engines-the-sans-io-contract) and hold no output queue (API-059, OI-56). A generator does not push a data field into the multiplexer. The framework feeds the generator a `Release` input; the generator returns the field as an action, and the framework feeds it to the multiplexer as an `Offer` input (LNK-076). §4 gives the inputs, actions, and bounds of every engine.

### 2.1 PacketGenerator (TM / AOS / USLP fixed-length; VC Packet and MAP Packet services)

Fills fixed-length frame data fields (TM data field, AOS M_PDU packet zone, USLP rule `000` TFDZ) with packets, inserted contiguously and in forward order, spanning frames as needed, and computes the FHP.

**Pointer values.** The offset counts from 0 at the first octet of the data field (TM), the Packet Zone (AOS), or the TFDZ (USLP).

| Protocol | FHP: no packet starts | FHP: only idle data | Source |
|---|---|---|---|
| TM (11 bits) | `0x7FF` | `0x7FE` | 132.0 §4.1.2.7.6.3–5, §4.2.2.4, §4.2.2.6 |
| AOS Issue 5 (M_PDU, 16 bits) | `0xFFFF` | `0xFFFE` | 732.0 §4.1.4.2.2.3–5, §4.2.2.4, §4.2.2.6 |
| AOS Issue ≤ 4 (11 bits) | `0x7FF` | `0x7FE` | AOS-003 |
| USLP rule `000` (16 bits) | `0xFFFF` | none: an idle TFDZ is one Encapsulation Idle Packet with FHP 0 | 732.1 §4.1.4.2.4.3–4, §4.2.2.1.4–5 |

USLP words the "no packet starts" case as "no packet starts nor ends within the TFDZ". A TFDZ in which a packet ends but none starts (the packet ends at the last octet and the next one starts in the next TFDZ, or the TFDZ holds the tail of a spanning packet that ends at its end) is not covered by the words; [OI-69](09-open-issues.md) asks.

### 2.3 ChannelMux (per physical channel; TM, AOS, fixed-length USLP)

Multiplexes VCs into master channels and master channels into the physical channel. It owns the MC and VC frame counters, inserts FSH/OCF/Insert Zone, and generates OID frames. It returns each frame as a `Transmit` action with the security ranges; the caller applies SDLS, and the codec writer computes the FHEC and the FECF (API-074).

## 4. Action bounds and output areas (API-057, API-062)

The bound `N` is the most actions one input can return (LNK-074); the area is the most octets one input can write to the caller's output area (LNK-075). Both are functions of the capacities of the engine's type. Symbols: *D* is the octets a field holds for the engine: the TM data field, the AOS M_PDU (header and packet zone), the USLP TFDF (header and TFDZ); *F* is the frame length of the physical channel (the Maximum Transfer Frame Length where it varies); *P* the Maximum Packet Length; *S* the maximum SDU size (LNK-073); *L* the maximum FDU (TC) or TFDF (USLP) length; *U* the maximum length of a data unit of the CLTU packer; *m* the shortest packet the engine delivers (7 for Space Packets, 3 for Encapsulation Packets, whose smallest non-idle packet is a 2-octet header and 1 octet of data; 1 when Encapsulation Idle Packets are delivered). The input-side storage (packet queue, assembly buffer, field slots) is state (API-060) and sets no area.

**Choices the Blue Book does not settle and that these bounds rest on.** The implementation SHALL meet them; each is stated as a requirement above.

- One `Release` returns at most one field, and the multiplexer keeps one field per VC (LNK-012, LNK-076). A different split of the work between the generator and the mux SHALL keep every value in the table.
- A Space Packet idle packet that does not fit leaves at most 6 octets of residue in the generator's state (LNK-013). The residue sets no action and no area: it is written into the next field's `DataField`.
- An extractor or reassembler reports a discard once per cause per input (LNK-061, LNK-070); a count of causes larger than the table would raise `N`.
