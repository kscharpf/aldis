# Briefing an agent

For the coordinator who dispatches an agent, and for the agent. A dispatched fork or subagent inherits [AGENTS.md](../../AGENTS.md); this file holds the conventions AGENTS.md does not carry. A brief names the task and links here.

## The brief

Name the goal, the base, what done means, and what the agent leaves alone: other pull requests, other tracks' directories ([roadmap §6](../08-roadmap.md)). Title the pull request of a work package `feat(m3/wp-4): Implement …` ([pr-body.md](pr-body.md)). Add what the agent cannot find in the repository: a decision already made in chat, a measurement to compare against, a pull request to stack on.

## Conventions for the agent

1. **Worktree.** Work in `.claude/worktrees/<branch>`, the path `scripts/reverify` and `scripts/cleanup-merged` expect, created from a fresh `git fetch origin`. The search boundary of AGENTS.md says what to search, not where to create a worktree. Run `source scripts/agent-env.sh`. Put temporary files in the session scratchpad. A `PreToolUse` hook (`.claude/hooks/base-checkout-guard.sh`, tested by `scripts/test-base-checkout-guard`) refuses Edit, Write, and NotebookEdit on a file in the base checkout outside `.claude/worktrees/`, for the coordinator as well. A `PreToolUse` hook on `Bash` (`.claude/hooks/detach-guard.sh`, tested by `scripts/test-detach-guard`) refuses a command that detaches a process: a background `&`, `nohup`, `disown`, or `setsid` (item 2).
2. **Waiting.** Start a command that runs longer than a minute (`cargo xtask check`, `scripts/reverify`, `gh run watch <id> --exit-status`) with `run_in_background`, and wait for its completion notification: it arrives when the command exits, and its output file holds the result. Do not write a poll loop (`until grep …`, `perl -e 'alarm …'`, `while pgrep …`), do not `sleep`, and do not read the output file while you wait: the harness blocks a foreground `sleep`, moves a command that runs longer than 180 s to the background anyway, and a hand-made wait that outlives its command has started a second run on top of the first. A turn that ends while work is pending notifies the coordinator, who must answer it, so end the turn with the final report only.
   - **Three tiers of `cargo xtask check`** (VER-068): `--quick` while editing (about a minute: format and `cargo check` of the root, `exerciser/`, `fuzz/`, and `crosscheck/`, every error at once); the default before each commit (it stops at the first failure); `--full` once before the final commit (adds coverage, `stack`, and `big-endian` when the gate would run them for the change; a missing tool is reported as skipped with the way to install it; the steps are chosen by the inputs the gate's checks declare, so a change of `Cargo.lock` or `xtask/` runs them too). A run that passed ends `check: quick tier ok (not a gate pass; …)`, `check: default tier ok (not a gate pass; …)`, or, for `--full`, `check: passed (full tier; …)` (`passed with skips` when a tool is missing); the skipped steps and the hints come before that last line. Report which tier passed, never "check passes" alone. The steps run under the gate's `RUSTFLAGS` and `RUSTDOCFLAGS` (`-D warnings`), so the first run after a change of those flags rebuilds. A coverage failure lists the missed lines as `path:line`; rerun one crate with `cargo xtask coverage -p <crate>`.
   - **One `cargo xtask check` at a time.** It takes a lock per worktree and refuses a second run with the holder's pid; wait for the first run's notification. Never `pkill` or kill a run to start another: the auto-mode permission check refuses it, and a killed run leaves a stale lock that the next run takes over.
   - **Resume after a failure.** `cargo xtask check --from <step>` skips the steps before the named one (the names it prints). Its last `check: partial` line says `not a pass`: the exit code is 0 for a passing partial run and is not the pass signal, that line is. After the fix, finish with a whole run of the tier you are reporting before you report that it passes.
3. **Gate.** Run `cargo xtask check --full` as the last run before you push (after merging `origin/main` too), push, and stop: the coordinator brings the pull request up to date and verifies it (AGENTS.md). A brief that gives you the gate says so; then merge `origin/main`, re-run `cargo xtask check --full`, push, run `scripts/reverify <pr>`, and confirm `cargo xtask verify check`. When `main` moves during the work, merge it again before the final run.
   - **One reverify per PR.** The script holds a lock per pull request, across worktrees: a second `scripts/reverify <pr>` while one runs prints the holder's pid and exits 3; `--wait` queues behind it. Different PRs run side by side.
   - **Leave the branch alone while a reverify runs.** `scripts/reverify --status <pr>` answers in one line with no network: `running` (exit 3), or the final line of the last run with the short head it is about (exit 0 when it succeeded, 1 when it did not, 5 when it timed out, 4 when none is recorded, which includes a run that aborted before its final line). The lock of a PR is released at its own final line, so a waiter does not wait for the PRs after it in the same call.
   - **Wait for the final line.** Run `scripts/reverify --status --wait <pr>` in the background (item 2); it returns once no reverify holds the lock and prints that line. A pid is not the signal: its process may be the lock's, a wrapper's, or your own.
   - **`--cancel` throws away the run in flight.** When `main` moved and the hosted run in flight is for a head that is already behind it, `scripts/reverify --cancel <pr>` (in the background, item 2) cancels that run, which also ends the reverify that is watching it, and then verifies the up-to-date head: you need not wait for a run that cannot merge. It cancels only the pull request's own run of a head that does not contain `main`, and it implies `--wait`. The cancelled run's work is lost: it publishes no record, so the next merge of `main` re-runs the checks whose inputs changed and reuses nothing from it (VER-060), and the watcher reports `cancelled`, not FAILED or STALE. Do not use it when the run is for a head that contains `main`, or when only documentation changed and a stacked refresh could reuse the record. Nothing cancels without the flag.
   - **Every wait times out.** `--timeout <min>` (default 60) bounds the wait for the hosted run: the script prints a final `#<n> TIMEOUT: ...` line naming the PR, the short head and the run id, records it, releases the PR's lock, and exits 5. It does not cancel the hosted run, and `--status` shows it (exit 5). A waiter behind another reverify (`--wait`, `--cancel`, `--status --wait`) follows the holder instead: the holder keeps a deadline in `<n>.deadline` next to the lock (now plus its own `--timeout`) and renews it at the start of each step (preparation, the local `verify --publish` or the hosted watch, each STALE retry, and while it queues for another lock). The waiter exits 5 with a TIMEOUT line when that deadline is more than 15 minutes overdue. That means the holder has gone 15 minutes past its own deadline without renewing it, which is not proof of a stall: `cargo xtask ci` and the local `verify --publish` have no bound, so check the holder's pid before you treat it as one. A lock without a deadline of its holder (an older script) is waited for for the waiter's own `--timeout` plus 15 minutes. That TIMEOUT records nothing and leaves the holder's lock. With several PRs, a failed one decides: exit 1 if any failed, else 5 if any timed out. Under `--cancel` the cancel comes first, so a queue TIMEOUT can leave the PR's run cancelled with no new run started.
   - **A STALE line is retried by the script.** When `main` moved during the run, `scripts/reverify` merges it, pushes, and verifies again, at most twice (`--stale-retries <n>`), and prints each retry. A FAILED line is a failure: read it, fix it, push, and run again.
4. **Pushes.** Confirm the pull request is open (`gh pr view <n> --json state`) before every push to its branch.
5. **Boundaries.** Stop at an open pull request, with a published record when the brief gave you the gate. Merging is the maintainer's. Leave other pull requests alone, and leave the worktree in place: the coordinator removes it after the merge.
6. **Measurement.** Measure on a throwaway branch: one full run of every check, the branch and its worktree deleted after the results are read. The record notes the run publishes under `refs/notes/verify` stay.

## The report

The pull request body follows [pr-body.md](pr-body.md). End the report with: the pull request URL; the evidence (command output, timings against the stated baseline, and the `verify check` result when you had the gate); **Judgement calls** (decisions the agent made under [decision-rights.md](decision-rights.md), each with its reason); **For the maintainer** (what only the maintainer can decide, as one question with a recommended option).

## For the coordinator

- Merge readiness of a pull request: `scripts/pr-status <n>...` prints the required contexts, the newest verify run, the review text, and a `READY` or `NOT READY: <reasons>` verdict. It says `NOT READY` when the head does not contain `origin/main` (`behind origin/main by <n>`), and when the newest review that does not itself end in the reply marker of [AGENTS.md](../../AGENTS.md) has no later review or PR comment that does (`review unanswered`); a review without findings needs a reply too, and an agent's review that ends in the marker needs none. `scripts/test-pr-status` tests it with no network and a stub `gh`.
- A fix round ends with a point-by-point reply on the review, quoting the commit.
- After a merge to `main`: refresh the next pull request with `scripts/reverify <n>`, or every open pull request behind `origin/main` in one call with `scripts/reverify --all-behind`. `scripts/test-reverify` tests the script with no network, no container, and no real `gh` or `cargo`; run it after changing the script. The verification check `shell` (VER-071, `scripts/check-shell`) runs shellcheck, a 100-column limit, and every `scripts/test-*` on the shell files of the repository.
- After a pull request merges: `scripts/cleanup-merged <branch>` shows what it would remove, and `--apply` removes the worktree and branches. It keeps a branch whose tip is not an ancestor of `origin/main`, a dirty worktree, and a branch without a merged pull request, and it stops a branch at the first step that fails. `scripts/test-cleanup-merged` tests it with no network and no real `gh`. `scripts/prune-agent-branches` clears leftovers in bulk.
