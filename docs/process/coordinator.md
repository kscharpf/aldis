# The coordinator's standing rules

For the coordinator: the main Claude session that dispatches agents, reviews, verifies, opens and readies pull requests ([decision-rights.md](decision-rights.md) §1). Each rule is a standing decision of the maintainer; the tag names the date it was made, and the reasons and incidents are in [history.md](history.md). What the coordinator may decide and what it asks is in [decision-rights.md](decision-rights.md); how to brief an agent is in [agent-brief.md](agent-brief.md).

## Dispatch

- **Delegate.** Do not implement pull-request-sized work yourself. Dispatch `wp-implementer` (Sonnet, [`.claude/agents/wp-implementer.md`](../../.claude/agents/wp-implementer.md)) with a self-contained brief ([agent-brief.md](agent-brief.md)) that carries every decision made in chat. Fork only when the work needs the chat's context: a fork inherits the parent model. Check an agent's claims with `scripts/pr-status <n>` before relaying them.
- **A fix-round brief says whether the round is final.** The final round, after the last review, runs the PR's check tier; an intermediate round runs `cargo xtask check --quick` plus `cargo test` of what it changed ([agent-brief.md](agent-brief.md) item 3).
- **Overlap check before dispatch.** Compare the paths the work will touch with the files of the open pull requests (`gh pr list --json number,files`). On an overlap, stack the work ([roadmap §6](../08-roadmap.md) rule 10), serialise it behind the other pull request, or combine the branches.
- **At most 2 subagents at once per coordinator session** (maintainer decision, 2026-11-09): implementers, reviewers and forks alike. Before dispatching, count the agents of yours still running; at 2, wait for one to finish.
- **Combine branches** of the same kind that touch overlapping or generated files into one pull request, unless one carries an open maintainer question, the kinds differ, or the diff would pass about 10k lines. Say what was decided (2026-10-24).
- **Don't ask about internals.** A choice internal to tooling that either way meets the specification: pick the smaller, reversible change and state it in the pull request. Ask only about what [decision-rights.md](decision-rights.md) reserves to the maintainer (2026-10-29).

## Review

- **Review with the reviewer agent.** Reviews use `reviewer` ([`.claude/agents/reviewer.md`](../../.claude/agents/reviewer.md)), fresh, given the pull request number and head only: never your conclusions or the implementer's report. When an implementer reports a pull request ready, dispatch `reviewer` at once, without waiting for the maintainer to ask; dispatch it again after each fix round ([review.md](review.md); 2026-11-07), except a comments-only round ([below](#a-comments-only-fix-round)).
- **Answer every review.** Watch open pull requests for reviews and comments. Every review (the reviewer agent's included) and every comment not written by an agent gets a point-by-point reply on the pull request quoting the fix commit; the reply ends in the marker of [AGENTS.md](../../AGENTS.md). A fix-round brief tells the implementer to post that reply (2026-10-21).
- **At most three reviews.** A pull request gets at most three reviews posted by `reviewer` (a review carrying the marker, not a comment; a review redone because it "does not count" ([review.md](review.md)) uses none of the three). After the third review the coordinator opens each remaining non-blocking finding and nit as a GitHub issue (one per finding, or one listing them, linking the review), then posts the reply naming the head and listing the issues (no implementer is dispatched); only the fix round is skipped. The pull request then goes to a train. If the third review has a blocking finding, do not dispatch a fourth on your own: add the label `needs-maintainer` (so `scripts/pr-status --train` does not pass it) and ask the maintainer, as one question with a recommended option (one more round limited to the blocking finding, or split or close the pull request) ([blocking: review.md](review.md#reporting-findings)).
- **Order inversions.** Tell the maintainer at once when they approve a pull request that depends (by branch ancestry or merge order) on an unreviewed one. Review latency in raw time is the maintainer's availability, not a process delay; count only active time.

### A comments-only fix round

The coordinator reads it instead of dispatching `reviewer` when all of these hold:

- **The reviewed head** is the `commit.oid` of the newest review whose body ends in the marker of [AGENTS.md](../../AGENTS.md), the review whose findings the round answers, not a head you read yourself: `gh pr view <n> --json reviews -q '[.reviews[] | select(.submittedAt != null and ((.body // "") | gsub("\\s+$"; "") | split("\n") | last) == "🤖 Generated with [Claude Code](https://claude.com/claude-code)")] | max_by(.submittedAt) | .commit.oid'` (the filter of `scripts/pr-status`).
- **The round did not rewrite the reviewed head or merge `main`:** `git merge-base --is-ancestor <reviewed head> <new head>` succeeds and `git rev-list --merges <reviewed head>..<new head>` prints nothing.
- **`git diff <reviewed head> <new head>` changes only** comments and doc comments in code (not a `// req:`, `// SAFETY:` or `// bound:` comment, nor a requirement ID or clause citation), or Markdown prose of `docs/milestones/` plans and checklists and the glossary. Anything else gets a fresh review: code, tests, generated files, requirement and OI rows, decisions, Blue Book readings, the rest of `docs/` (profiles, standards chapters, `docs/verification/`, `docs/process/`), `AGENTS.md`, `.claude/agents/`.

Read the whole diff and confirm it fixes what that review asked and nothing more; if it does not fix a finding, or changes more than was asked, dispatch `reviewer`. Otherwise post a comment naming both heads, saying you read the diff, and ending in the marker, only after checking that the implementer's reply naming the new head is on the pull request: `scripts/pr-status` does not tell the two comments apart (maintainer decision, 2026-11-08).

## Verification

- **Verify after review.** A pull request's first verify run starts only once its review is in and any fix round is pushed (2026-11-05). Two exceptions: a pull request stacked under [roadmap §6](../08-roadmap.md) rule 10 may verify while the pull request below it is in review; and a brief that grants the gate ([agent-brief.md](agent-brief.md) item 3) is the coordinator's choice to verify before review, made only when no review round is expected.
- **Don't wait on an agent's report.** When an implementer fixes a gate failure, start `scripts/reverify --alone <pr>` as soon as the new head is on the pull request branch, for a pull request that merges alone (2026-10-31).
- **Waiting on `scripts/reverify`** (flags, exit codes, locks, deadlines and timeouts: its header, `scripts/reverify --help`):
  - Leave the branch alone while a reverify runs. `scripts/reverify --status <pr>` answers in one line with no network.
  - To wait for the final line, run `scripts/reverify --status --wait <pr>` in the background ([agent-brief.md](agent-brief.md) item 2). A pid is not the signal: it may be the lock's, a wrapper's, or your own.
  - `--cancel` throws away the run in flight. Use it only when `main` moved and the hosted run in flight is for a head that is already behind it; do not use it when the run is for a head that contains `main`, or when only documentation changed and a stacked refresh could reuse the record. Nothing cancels without the flag.
  - A queue TIMEOUT means the holder went 15 minutes past its own deadline without renewing it; that is not proof of a stall (`cargo xtask ci` and the local `verify --publish` have no bound), so check the holder's pid before you treat it as one.
  - A STALE line is retried by the script (at most twice, `--stale-retries <n>`). A FAILED line is a failure: read it, fix it, push, and run again.
  - **Open-issue table conflicts.** Take the next free `OI-<number>` for a new open issue ([09](../09-open-issues.md)). When two PRs append a row, `scripts/reverify` finishes the merge of `origin/main` in `docs/09-open-issues.md` by keeping both sides in number order and printing `#<n>: kept both sides of an OI table conflict; check for duplicate IDs`, only when that file is the sole conflicted file and every hunk is a pure append; any other conflict is undone and reported. A duplicate number or title then fails `cargo xtask spec-lint` (also in the gate's `spec` check) and names the rows: for a duplicate number renumber your own row and its references; for a repeated title keep one row. Push, and run reverify again.
- **Merge readiness.** `scripts/pr-status <n>...` prints the required contexts, the newest verify run, the review text, and a verdict: by default the merge gate's, `READY` or `NOT READY: <reasons>`, for a pull request that merges alone and for a train PR (head branch `train/*`); with `--train` the verdict of a constituent of a train (it asks for no record and no merge of `main`: [Merge trains](#merge-trains)), `READY FOR TRAIN` or `NOT READY: <reasons>`. The flag may stand anywhere. The default verdict says `NOT READY` when the head does not contain `origin/main` (`behind origin/main by <n>`); every verdict says it when the newest submitted review has no later pull request comment (`gh pr comment`) whose last line is the reply marker of [AGENTS.md](../../AGENTS.md) (`review unanswered`); a review without findings, and a review that itself ends in the marker, need a reply too, and a later review is not a reply.
- **No admin bypass.** Never propose force-merging or bypassing branch protection, even during a CI outage; a fallback keeps the same verification (2026-10-22).

## After a merge to main

- **Refresh the next pull request, if it merges alone or is the train PR.** A pull request that will ride a train is not refreshed after a merge: [Merge trains](#merge-trains). Keeping pull requests up to date needs no question ([decision-rights.md](decision-rights.md) §2.11, §4, §5). The order is what this rule adds: refresh the next pull request in the agreed merge order first, and start its run at once: `scripts/reverify <n>`, or every open pull request behind `origin/main` with `scripts/reverify --all-behind`. On a conflict in a generated file, regenerate it; never hand-merge it (2026-10-24). After changing a script, run its offline `scripts/test-<name>` (`test-reverify`, `test-train`, `test-cleanup-merged`, `test-pr-status`; no network). The `shell` check (VER-071, `scripts/check-shell`) runs shellcheck, a 100-byte line limit, and every `scripts/test-*` on the shell files of the repository.
- **Clean up.** `scripts/cleanup-merged <branch>` (dry run, then `--apply`). It keeps a branch whose tip is not an ancestor of `origin/main`, a dirty worktree, and a branch without a merged pull request (the tests, including the closed-pull-request cases of maintainer decisions 2026-11-08 and 2026-11-09, are in the script's header). The auto-mode permission check refuses raw `git worktree remove` and `git branch -D` (2026-10-21). `scripts/prune-agent-branches` clears leftovers in bulk (see Multiple coordinators).
- **The base checkout stays current.** `scripts/cleanup-merged --apply` ends by fast-forwarding the main checkout's `main` to `origin/main` (with a warning and no change if it is not on `main`, is dirty, or cannot fast-forward), because sessions and subagents read AGENTS.md there (maintainer, 2026-11-10).
- **No bookkeeping commits.** Never a commit just for a pull request number or a status row. Record a maintainer answer where [decision-rights.md](decision-rights.md) §1 says, batched into the change it governs before the final verify run (2026-10-24).

## Merge trains

Decision of the maintainer, 2026-11-07 ([decision-rights.md](decision-rights.md) §2.10): every merge to `main` made every other open pull request stale, so verification runs once on a train. GitHub's merge queue is not available on a user-owned repository, so a train is built from ordinary branches and pull requests.

- **What a pull request needs.** Its own independent review ([review.md](review.md); a comments-only fix round may be read by the coordinator instead, [a comments-only fix round](#a-comments-only-fix-round)) and the implementer's reply, as before. It needs no verify record and no merge of `main`: verification runs on the train only, and the merge gate (VER-058) applies to the train PR. `scripts/pr-status --train <n>` says `READY FOR TRAIN` only when the PR has at least one review, the review has a later reply ending in the marker that names the current head (a hex prefix of at least 7 characters, so a push after the reply is caught), the head branch was not force-pushed after the reply, and the PR carries no label `needs-maintainer`.
- **Only the maintainer assigns pull requests to trains** (maintainer decision, 2026-11-09). Build, rebuild or merge a train only when the maintainer names its pull requests and their order in your chat, and never add a pull request to a train on your own. `scripts/train` refuses a real build while another `train/*` PR is open (`--allow-open-train` overrides it; use it only when the maintainer names it).
- **Ownership.** One train for all scopes, run by the process coordinator. A scope coordinator hands over its ready pull requests (reviewed, review answered) by number and keeps the rest of its duties ([Multiple coordinators](#multiple-coordinators)). The merge order stays the maintainer's; the train lists the pull requests in that order.
- **Out of trains.** A pull request that waits on a maintainer decision (a breaking C ABI change, a requirement amendment) until it is decided. Mark it with the label `needs-maintainer` (the repository must have the label; the coordinator adds it when it opens or finds such a PR and removes it when the maintainer answers): `scripts/pr-status --train` says `NOT READY` for it and `scripts/train` refuses it. A pull request that merges alone is refreshed and verified as before, with `scripts/reverify --alone <pr>`: `scripts/reverify` refuses a pull request whose head branch is not `train/*` without `--alone`, and `--all-behind` covers only `train/*` pull requests.
- **Build.** `scripts/train <pr>...` builds the train branch `train/<YYYY-MM-DD>-<n>` and opens the train PR (`chore(train): …`; [pr-body.md](pr-body.md)); it refuses a pull request that is not `READY FOR TRAIN`, and one pushed to after its check (details: the header of `scripts/train`). Do not stack a pull request that depends on one outside the train. Verify the train PR once: `scripts/reverify <train-pr>`. `scripts/train --dry-run <pr>...` builds the same merges and removes its branch and worktree again.
- **Preflight.** Before you propose a train to the maintainer, and again before you build it, run `scripts/train --plan <pr>...` with the pull requests in the proposed order. It trial-merges the exact heads with no worktree and no push, in seconds, and prints the conflicts (the first pull request named is where a build would stop) and any `lockfile needs regenerating: <path>` (output: the header of `scripts/train`). It exits 1 on a conflict: propose the train without the pull request it names, or send that one back first. `scripts/pr-status --train` also says `NOT READY: conflicts with origin/<base>: <paths>`.
- **Lockfiles.** `scripts/train` resolves a conflict whose only paths are `Cargo.lock` files and regenerates a stale lockfile in a commit on the train branch (`chore(train): regenerate <path> …`; the rules: its header). A package version that the incoming pull request's lock introduced and the result lacks, such as a deliberate `cargo update`, makes it a conflict: leave the pull request out and return it. A manifest bump takes the newest cached version, so read the printed line and the diff of the commit. Never hand-merge a lockfile. Any other conflict still stops the build.
- **Dispatch against open pull requests.** Before dispatching a work package, compare the files it will likely change with the files of the open pull requests (`gh pr list --json number,files`). Run a wide refactor (most crates, or an `xtask` registry) alone, not alongside a feature wave.
- **Mechanical conflicts.** A conflict in a doc table, a lockfile, or a generated file gets an immediate narrow fix-up dispatch (or your own fix on that file); do not wait for the owner's next round.
- **Stacked pull requests** ([roadmap §6](../08-roadmap.md) rule 10): a pull request stacked on another rides the same train as its base, after it; `scripts/train` refuses a PR whose base branch is not `main` unless the PR of that base branch is earlier in the same train. It is not verified on its own: the train PR is, and `scripts/reverify` without `--alone` refuses it.
- **Conflict.** Two pull requests that conflict while the train is built (the preflight finds it first): the script stops, names the later one in the agreed order, and pushes nothing. Leave that pull request out, build the train without it, and return it to its owner to merge `main` and resolve.
- **Failure.** When the train's verify run fails, find the pull request that caused it (read the failing check, else bisect by building the train without a pull request and verifying again), drop it with `scripts/train --rebuild <train-pr> --without <pr>`, which closes the failed train PR and opens the next one, verify it, and return the dropped pull request to its owner with the failure. The owner fixes it, and it rides a later train.
- **Merge.** The maintainer approves and merges the train PR with a merge commit, never squash or rebase, so that `cargo xtask changelog` reads each constituent from the merges between the first and second parent of the merge commit ([pr-body.md](pr-body.md)). The heads of the constituents are then in `main` and GitHub marks them merged, so `cargo xtask status-table` and `scripts/cleanup-merged <branch>` see them as before. The train PR itself has no changelog entry and no status row. If `main` moves before the train merges, refresh the train PR (`scripts/reverify <train-pr>`), not its constituents. Clean up the train branch and worktree like any merged branch.

## Reporting to the maintainer

- **Nightly metrics.** After each "Process metrics" report (pinned issue #87, VER-063), compare it with the previous one. When a process-created wait worsens, propose a fix with the numbers. Never change the gate; changes go to the maintainer as proposals.
- **Weigh mechanism cost.** A proposed check or tool states how often the problem occurred and how large the mechanism is. Prefer detection plus a manual fix, or a reviewer rule, when classification needs judgement. When reviews keep finding new edge cases in a mechanism, offer a smaller design.

## Changing the process

- **Only by pull request.** Said once, in [AGENTS.md](../../AGENTS.md) (the sentence on dispatching an agent). Branches for process changes take the prefix of [roadmap §6](../08-roadmap.md) rule 3.

## Multiple coordinators

The maintainer may run several coordinators at once (decision of 2026-11-06).

- **Scope.** Each coordinator is its own Claude session in the base checkout, named after its scope. Each owns one milestone in flight (for example A1); one owns process work.
- **Ownership.** A pull request belongs to the coordinator of the milestone its title scope names (`a1/…`; [pr-body.md](pr-body.md)). Any other pull request belongs to the process coordinator. Except for the cross-scope duties below, a coordinator dispatches, reviews, refreshes, and cleans up only its own pull requests and their branches (`scripts/cleanup-merged`). While more than one coordinator runs, only the maintainer runs `scripts/prune-agent-branches --apply`: it removes any clean worktree whose branch is an ancestor of `origin/main` or whose remote branch is gone, including a peer's new worktree that has no commits yet. Leftover `worktree-agent-*` branches wait for that prune.
- **Cross-scope duties** belong to the process coordinator: the nightly metrics duty, flagging order inversions across scopes, and refreshing other scopes' pull requests after a merge (those that merge alone) and running the merge train ([Merge trains](#merge-trains)). A scope coordinator may refresh its own pull requests too. While several coordinators run, every refresh uses `--wait` (`scripts/reverify --wait <pr>…`; the process coordinator uses `--all-behind --wait`): without it a call exits 3 and refreshes nothing when any lock is held. With no process coordinator running, these duties wait. The merge order across scopes stays the maintainer's.
- **Context.** A coordinator's working context stays in its session and reaches agents through briefs. It resumes from GitHub: the plan's status table (`cargo xtask status-table`), its open pull requests, and the open issues. Decisions go where [decision-rights.md](decision-rights.md) §1 says; lessons go in as process pull requests. Nothing specific to one scope goes into the shared auto-memory, which every coordinator in the checkout reads.
- **Talking to peers.** Before dispatching work that touches a shared file ([roadmap §6](../08-roadmap.md) rule 2, and generated files), or when a change affects another scope, send the owning coordinator a message by its session name with the one fact that matters, not a transcript. It is a notification, not a record, and is never posted as a pull request comment: `scripts/pr-status` would read it as a reply to the review. With no peer session running, send none; the peer sees the change when it resumes from GitHub, and a conflict surfaces at the merge of `main`. The overlap check against open pull requests still applies. The repeated-conflicts row of the metrics report (#87) measures whether this is enough; add a claim mechanism only if that row rises.
