# Milestone A3 — COP-1

**Goal:** the uplink of the reference application becomes the Sequence-Controlled (AD) service of COP-1. The ground node sends every Frame Data Unit as a Type-AD frame through `Fop1` (K = 4, T1_Initial = 1 s, Transmission_Limit = 3), feeds it the CLCW of every downlink frame, and issues the FOP-1 directives of the ops script (*Initiate AD Service*, with Unlock where a case needs it); the flight node accepts frames through the whole of `Farm1` (W = 8, retransmission allowed) and reports its state in the CLCW of every frame. The harness injects loss, duplication, delay, and a lockout into the uplink, and the traces show the retransmission, the timeout, the alerts, and the recovery. The headline case is a COP-1 retransmission over a lossy link. From A3 on the link-level traces are frozen (APP-004). The packet projection of the nominal case stays that of A1 (APP-003) ([reference-application.md](../reference-application.md) §4.2, §6, §7.4).

### WP-1 Scenario additions (S) — area APP, no code

## 5. Risks

| Risk | Mitigation |
|---|---|
| A frozen trace (APP-004) freezes a defect, and A5, A6, ACFS, and AINT then copy it; the engines make the traces, so an engine defect looks like the expected behaviour | D8: strict decoding of every frame, a hand check of the first frame of each kind, an independent regeneration of the headline case, and retransmission schedules derived by hand in WP-1 before any node exists, so the blessed trace is compared with them and not only with itself |
| T1_Initial (1 s) is close to the delay of queued retransmissions, since D3 sends one frame per 250 000 µs slot: after a loss with several frames behind it, the last retransmission leaves up to a second after the order, and T1 may expire for frames that are on their way | The 395 000 µs of §4.2 is the sum for one frame; WP-1 derives the schedule of `a3-uplink-loss` with the window of four and states the instants, and T1_Initial = 1 s stays (maintainer, 2026-11-11): if the derivation shows a spurious timeout it goes back to the maintainer as a decision, and the plan does not change the value itself (232.1 §5.1.9.2 gives the formula; a change would be a new decision, not a silent one) |
| Fault scripts address units by index as sent, and a retransmission is a unit, so a fault intended for the first copy can hit a retransmitted one if the schedule is derived from the nominal case | The indexes of each case are derived from its own schedule (WP-1); the harness reports the unit a fault hit in the `fault` record, and the golden trace shows it |
| The lockout case relies on the *Set V(S)* directive to make valid frames fall in FARM-1's lockout area; the recovery needs the right order of *Set V(S)* and *Initiate AD Service (with Unlock)*, whose acceptance by state is a Blue Book matter | The readings of §2 are checked in WP-1 before the case is written; if the directives do not allow the sequence, the case's script changes in WP-1 (still before any trace exists), and no new fault kind is needed unless the maintainer wants one |
| A directive or notification the engines expose but the scenario does not need is left out, and AINT or ACFS then finds a cell the cases did not reach | The M3 vectors cover every cell of both tables (COP-005); A3 reaches the cells of D5, and the rest is listed by WP-5's coverage of the cases against the tables, so that the gap is known |
| OI-98 (an unknown MAP ID in a frame that FARM-1 would accept) reaches the AD service: a frame refused at validation is not acknowledged, FOP-1 retransmits it, and the CLCW never advances | No A3 case sends such a frame; the resolution of OI-98 is the maintainer's and, if it moves the check, affects the receiving path of WP-3 only |
| The `a2-*` traces change by accident when the nodes gain the AD path | WP-2 and WP-3 keep the `frames` path as it is and every pull request runs `compare` for all cases; D2 makes the path a choice of level |
| FARM-1 used through the C ABI handle (ACFS P3) cannot do what the Rust node does (for example, the caller-owned buffer or the CLCW read) | D4 states the use in the scenario document in terms the handle offers (§1.1); a gap is filed as `api-feedback` for track R, and the plan does not go beyond the handle |
| FOP-1 carry-overs parked for v1.1 surface in A3: #254 (a `Fop1Decision` can be committed to another engine or after a state change) and #235 (hand-off of Segment Header FDUs and per-FDU TFDF headers to FOP-1) | The A3 nodes commit each decision at once to the engine that made it. If a work package finds that A3 needs either, or is hurt by either, it stops at that point and raises it to the maintainer through the coordinator (#490); it does not work around it in the node, and neither issue is fixed inside a refapp pull request |
