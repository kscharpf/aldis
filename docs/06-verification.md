# 06 — Verification (mission-grade assurance)

**Assurance target:** *mission-grade*. The code is designed so that a later qualification against a specific standard (e.g. NASA NPR 7150.2 Class B/C, ECSS-E-ST-40C/Q-80C, DO-178C) needs evidence collection rather than redesign. This document does **not** claim compliance with any of those standards.

## 7. Verification runs and the merge gate

The checks of this specification run on the contributor's machine, not on a hosted CI service that every pull request waits for. A pull request merges on the evidence record of a verification run, made on the contributor's machine or, when the contributor asks for it, on a GitHub-hosted runner (VER-060); GitHub Actions repeats every check each night as an independent run ([open issues](09-open-issues.md) OI-31).

Wherever this specification, a profile, or a milestone plan says that a check runs **in CI**, or names a CI job or a CI target, it means that check in the verification run of VER-056. A check that only runs at night says so.

A run leaves out a check whose inputs are identical to those of an earlier commit in whose published record the check passed, and takes that result (VER-056). This is sound because a check that sees the same inputs gives the same result. Its inputs include the run itself (`xtask/` and the files the image is built from), so the same inputs also mean the same script, image definition, and pinned tools. Usually the earlier commit is the one whose record covers the tip of `main`: branches merge only when up to date (VER-058), so a merge commit on `main` has the tree of the pull-request head whose record passed. After `main` moves and the branch merges it, the earlier commit can be the branch's own verified head, when the commits brought in from `main` touch none of the check's inputs. The run names the record in which the check actually ran, not a record that took the result from another, and `verify check` re-derives each result taken from git and that record rather than trust the chain in between. A commit pushed to `main` directly, a squash or rebase merge, or a merge of a branch that was not up to date has no covering record; then a check runs unless an earlier commit of the branch has its inputs. All of this rests on the input lists being complete, as skipping did before: a path that a check reads but does not list lets a change to that path go unchecked until the nightly runs (VER-059), which run every check on `main` regardless. A taken result may come from a run on another host: the other Linux architecture, or macOS for the macOS-only check.

A local run needs Podman or Docker Engine (VER-056) with about 20 GB of free disk space and 6 GB of memory for the engine's VM (`podman machine set --memory 6144`). The first run builds the image (several GB of downloads). On macOS, a Podman VM keeps the disk space the build frees until it is trimmed: run `podman machine ssh sudo fstrim -av` after the build.

The coordinator runs the gate; implementation agents commit and stop. On the branch's head, pushed first because the commit must be on GitHub before its status can be set:

```sh
cargo xtask verify --publish   # every check the change needs, in the pinned image, stopping at the first failure; then the git note and the status aldis/verify
cargo xtask verify check       # re-check the published record of HEAD; it fails while HEAD lacks the tip of main
```

The hosted run MAY make the checks in four parallel jobs (VER-067): `cargo xtask verify part <group>` runs the checks of one group (`host`, `cross`, `coverage`, `embedded`) and writes a part record, and `cargo xtask verify assemble [--publish] <part record>...` makes the one record from the four, refusing parts that do not fit together; a part record is that of an `--only` run, so it never passes the gate by itself. The hosted run builds from scratch in the pinned image: no persistent build cache is restored into it, so a record's evidence comes from the checked-out sources and the image alone. If a record published by another run in between changes the plan of a stage, `verify assemble` refuses the parts as not fitting together; dispatch the run again. `cargo xtask verify list` names the checks HEAD needs; `--only <check>,...` runs a subset while working, which never passes the gate. A record is tied to the commit's tree, so any new commit, including a merge from `main`, needs a new run. If `main` moves during a passing run, `--publish` still publishes the record for reuse but sets no `aldis/verify` status: merge `main` and verify again. `scripts/reverify <pr>...` does that for open pull requests: merge `origin/main`, run `cargo xtask ci`, push, and then verify the head. When `cargo xtask verify list` says that no container would be started (the input rule skips or reuses every gating check, as it does for a stacked pull request whose base has merged: [roadmap §6](08-roadmap.md#6-working-in-parallel) rule 10), it runs `cargo xtask verify --publish` itself, which needs no image and no engine (on a macOS host it also runs the host-bound `test-macos` check, about two minutes, since no hosted record has a passing result of it to reuse); otherwise it dispatches the run of VER-060 on a GitHub-hosted runner (every such PR is prepared and dispatched first, then the runs are awaited together). It reports each conclusion, labelling a run that did not succeed STALE when the head lacks the tip of `origin/main` (merge it and run again; the record is published for reuse) and FAILED otherwise. To start that run by hand: `gh workflow run verify.yml --ref <branch>`, then `gh run watch`, then `cargo xtask verify check`. The run is three stages: `prepare` builds `xtask` once for the other jobs and makes sure the registry has the image (and builds and pushes it when it has not), four `part` jobs run the groups side by side, and `assemble` makes and publishes the record. The parts and `assemble` install no Rust toolchain: the checks run in the image. It takes about 7 minutes, and 20 to 30 more when `prepare` has to build the image.

## 9. Process metrics

The development process is measured, so that its friction is data rather than anecdote. `cargo xtask metrics` reads the merged pull requests from GitHub and the published records (VER-057) and reports, for each pull request and for the period, how long it took, how big it was, what its verification cost, how often its branch merged `main` and in which files that conflicted, and what its reviews led to. It also measures the **process overhead**: how much of the work went to the process rather than the product. A changed path is *product* in `crates/`, `cpp/`, `include/`, `test-vectors/`, `specs/`, `exerciser/`, `fuzz/`, `refapp/`, `crosscheck/`, and `difftest/`, and in the specification, which is `docs/` except its process parts (the requirement documents `docs/0*.md`, `docs/profiles/`, and `docs/standards/`, and the index, the glossary, and the reference application); it is *process* in `xtask/`, `.github/`, `docs/process/`, `docs/verification/`, `docs/milestones/`, `changelog.d/`, `AGENTS.md`, and the other root files. A commit is *bookkeeping-only* when it changes nothing but the work-package status rows of a milestone plan or verification records. It needs the network and `gh`, so it is never part of `cargo xtask ci` or a gate: it reports, and the maintainer decides. The report is kept in the pinned issue "Process metrics", refreshed each night; the milestone exit reviews it ([checklists](milestones/checklists.md#milestone-exit)).

## 11. Hazard analysis and assurance case

The [hazard and failure-mode analysis](verification/hazards.md) lists how a failure of the library could harm a mission and what controls each failure mode; the [assurance case](verification/assurance-case.md) argues from the library's top claims down to the requirements and the evidence that support them, and takes each hazard's controls as evidence. [assurance-evidence.md](verification/assurance-evidence.md) specifies how `cargo xtask assurance` checks both. Both were added to M2 WP-8 by the maintainer on 2026-10-24.
