# 06 — Verification (mission-grade assurance)

**Assurance target:** *mission-grade*. The code is designed so that a later qualification against a specific standard (e.g. NASA NPR 7150.2 Class B/C, ECSS-E-ST-40C/Q-80C, DO-178C) needs evidence collection rather than redesign. This document does **not** claim compliance with any of those standards.

## 7. Verification runs and the merge gate

The checks of this specification run on the contributor's machine, not on a hosted CI service that every pull request waits for. A pull request merges on the evidence record of a verification run, made on the contributor's machine or, when the contributor asks for it, on a GitHub-hosted runner (VER-060); GitHub Actions repeats every check each night as an independent run ([open issues](09-open-issues.md) OI-31).

Wherever this specification, a profile, or a milestone plan says that a check runs **in CI**, or names a CI job or a CI target, it means that check in the verification run of VER-056. A check that only runs at night says so.

A run leaves out a check whose inputs are identical to those of an earlier commit in whose published record the check passed, and takes that result (VER-056). This is sound because a check that sees the same inputs gives the same result. Its inputs include the run itself (`xtask/` and the files the image is built from), so the same inputs also mean the same script, image definition, and pinned tools. Usually the earlier commit is the one whose record covers the tip of `main`: branches merge only when up to date (VER-058), so a merge commit on `main` has the tree of the pull-request head whose record passed. After `main` moves and the branch merges it, the earlier commit can be the branch's own verified head, when the commits brought in from `main` touch none of the check's inputs. The run names the record in which the check actually ran, not a record that took the result from another, and `verify check` re-derives each result taken from git and that record rather than trust the chain in between. A commit pushed to `main` directly, a squash or rebase merge, or a merge of a branch that was not up to date has no covering record; then a check runs unless an earlier commit of the branch has its inputs. All of this rests on the input lists being complete, as skipping did before: a path that a check reads but does not list lets a change to that path go unchecked until the nightly runs (VER-059), which run every check on `main` regardless. A taken result may come from a run on another host: the other Linux architecture, or macOS for the macOS-only check.

A local run needs Podman or Docker Engine (VER-056) with about 20 GB of free disk space and 6 GB of memory for the engine's VM (`podman machine set --memory 6144`). The first run builds the image (several GB of downloads). On macOS, a Podman VM keeps the disk space the build frees until it is trimmed: run `podman machine ssh sudo fstrim -av` after the build.

## 8. Inspection records and their approval

Requirements verified by inspection (method **I**) are traced by records in [`verification/records/`](verification/records/) ([analysis-records.md](verification/analysis-records.md)). The inspections of GEN-022 and GEN-023, one per crate, are kept in [`verification/inspections/`](verification/inspections/): every loop with its bound, the call graph, and every blocking construct. They change with almost every work package, so the work is split: whoever changes the code prepares the revision, and the maintainer approves the revisions together, once per milestone (maintainer decision 2026-10-21).

## 9. Process metrics

The development process is measured, so that its friction is data rather than anecdote. `cargo xtask metrics` reads the merged pull requests from GitHub and the published records (VER-057) and reports, for each pull request and for the period, how long it took, how big it was, what its verification cost, how often its branch merged `main` and in which files that conflicted, and what its reviews led to. It also counts the maintainer's decisions in `docs/process/decisions.md`, once that log exists, and measures the **process overhead**: how much of the work went to the process rather than the product. A changed path is *product* in `crates/`, `cpp/`, `include/`, `test-vectors/`, `specs/`, `exerciser/`, `fuzz/`, `refapp/`, `crosscheck/`, and `difftest/`, and in the specification, which is `docs/` except its process parts (the requirement documents `docs/0*.md`, `docs/profiles/`, and `docs/standards/`, and the index, the glossary, and the reference application); it is *process* in `xtask/`, `.github/`, `docs/process/`, `docs/verification/`, `docs/milestones/`, `changelog.d/`, `AGENTS.md`, and the other root files. A commit is *bookkeeping-only* when it changes nothing but the decision log, the work-package status rows of a milestone plan, or verification records. It needs the network and `gh`, so it is never part of `cargo xtask ci` or a gate: it reports, and the maintainer decides. The report is kept in the pinned issue "Process metrics", refreshed each night; the milestone exit reviews it ([checklists](milestones/checklists.md#milestone-exit)).

## 10. Decision rights

Which decisions need the maintainer, and which the coordinating session or the agent of a work package takes, is set by the [decision rights](process/decision-rights.md). The maintainer's decisions are indexed in the [decision log](process/decisions.md), one line each, so that a later reader finds them without reading every pull request (maintainer request 2026-10-21).

| ID | Requirement | Source | Verif. |
|---|---|---|---|
| VER-062 | A decision SHALL be taken by the role that the [decision rights](process/decision-rights.md) give it to: the maintainer, the coordinator, or the agent of a work package. A decision they give to the maintainer SHALL NOT be taken by another role, and a pull request that depends on one SHALL NOT be readied for merge until the decision is recorded. Every decision the maintainer takes SHALL be recorded where the decision rights say and, in the pull request that records it (or, for a decision no pull request records, the next one the coordinator opens), as one line of the `## Log` of [`docs/process/decisions.md`](process/decisions.md): `- YYYY-MM-DD · <category> · <#N or chat> · <decision>`, with a category slug that the decision rights define, the lines in date order. `cargo xtask decisions` SHALL check that format, in `cargo xtask ci` and the verify check `spec`.
