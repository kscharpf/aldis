# AOS Transfer Frame — CCSDS 732.0-B-5

**Crate:** `aldis-aos` · **Reference:** `specs/pdf/732x0b5ec1.pdf` ([how to download](../../specs/README.md)) · **Acronyms:** [glossary](../glossary.md)

## 1. Wire format (§4.1)

The field layout is that of the Blue Book clause cited in the heading, and of the rustdoc of the view and writer types; the vectors pin the octets.

The data field holds exactly one of: an **M_PDU** (packets), a **B_PDU** (bitstream), a **VCA_SDU**, or Idle Data (OID frame), fixed per VC.

- **M_PDU (Issue 5):** First Header Pointer (16 bits) ‖ Packet Zone. FHP `0xFFFF` = no packet starts; `0xFFFE` = only idle data.
- **B_PDU:** Reserved Spare (2 bits, `00`) ‖ Bitstream Data Pointer (14 bits, index of the last valid *bit*) ‖ Data Zone. Pointer `0x3FFF` = all valid; `0x3FFE` = only idle. The view reports a pointer `p` below the reserved values as `ValidBits(n)` with `n = p + 1`, the number of valid bits (GEN-053), a `ValidBitCount` of 1 to `0x3FFE`, the counts whose pointer lies below the reserved values (RS-020).

## 2. Editions

Issue 5 extended the SCID to 10 bits using former spare bits 42–43, and the M_PDU First Header Pointer to 16 bits (to allow frames up to 65 536 octets). Missions on Issue ≤4 are not wire-compatible.

## 3. Configuration (managed parameters, §5)

The managed parameters are those of the Blue Book clause cited in the heading; the configuration types carry them, with their ranges, in their rustdoc.

There is **no OCF flag in the AOS header**. OCF presence is a per-VC managed parameter, so decoding requires the VC configuration. The codec keeps the physical channel in `AosPhysicalChannelConfig` and the virtual channels, each with its SCID, in `AosVirtualChannelConfig`; the valid SCIDs of the physical channel and the valid VCIDs of each master channel are those of the configured virtual channels, which a `VcTable<N>` holds (at least one, AOS-020) and the decoder and writers reach through the `VcLookup` trait (M2 plan D14). An M_PDU or B_PDU VC needs a data field of at least three octets, its 2-octet header and a zone octet, since the zone is mandatory (§4.1.4.2.1.3 b, §4.1.4.3.1.3 b).

**Frames on VCID 63.** OID frames (§4.1.4.1.5) have no virtual channel parameters: Table 5-3 configures VCIDs 0–62 only. The codec reads and writes them with no `VC_OCF` (§4.1.5.2 makes the OCF a per-VC parameter) and no Security Header or Trailer (Table 6-1 is per VC), and with the Insert Zone and the FECF when the physical channel has them (§4.1.3.3, §4.1.6.1.3). An OID frame of an SCID with no configured VC is `UnknownChannel` (`spacecraft_id`; §4.3.6.3). The maintainer settled this reading on 2026-10-24 ([OI-43](../09-open-issues.md) item 1).

| AOS-013 | The FHEC codec SHALL implement the Reed-Solomon (15,11) code over GF(2⁴), shortened by 5 symbols and converted to a binary (40,24) code: 4-bit symbols (J = 4), correction of up to two symbol errors (E = 2), field generator polynomial F(x) = x⁴+x+1, code generator polynomial g(x) = (x+α⁶)(x+α⁷)(x+α⁸)(x+α⁹), systematic. Symbols 1–5 are virtual fill: all zeros, at the start of the codeword only, never transmitted. Symbols 6–11 are header bits 0–15 and 40–47 (4 bits each, the leftmost bit transmitted first); symbols 12–15 are the parity symbols in bits 48–63. Counted in transmitted symbols the code is (10,6), the name 732.0-B-4 §4.1.2.6.5 gives the same code; one implementation serves both editions (OI-04, OI-35 item 6). | §4.1.2.6.5 a–h; 732.0-B-4 §4.1.2.6.5 | V |
| AOS-014 | On decode with FHEC configured, the codec SHALL correct up to two symbol errors in the ten transmitted symbols (header bits 0–15 and 40–63) before any header field is read, and the view SHALL report the number of corrected symbols (0, 1, or 2) in both modes; a correction is not an anomaly (OI-33). When no pattern of at most two symbol errors in the transmitted symbols accounts for the syndromes, decoding SHALL fail with `HeaderUncorrectable` in both modes. With three or more symbol errors the decoder can return a wrong header as corrected, and no decoder can prevent it: the code's minimum distance is 5 (n − k + 1 for the (15,11) code, unchanged by shortening), so it guarantees two corrections and nothing beyond, and some patterns of three or more errors lie within two symbols of another codeword. `HeaderUncorrectable` is therefore reported only for the patterns the decoder detects (OI-35 item 5). When an FECF is configured, it SHALL be checked over the frame with the corrected header: the sender computes it over the transmitted header, and the receiving end corrects the header before it checks the FECF. A miscorrected header then fails with `CrcMismatch`, unless the CRC also misses the difference. The VC Frame Count (bits 16–39) is not protected and SHALL NOT be altered. | §4.1.2.6.1 notes 1–2; §4.1.2.6.5 b, note 3; §4.1.6.2; §4.3.7.2–3 | V |
| AOS-015 | The Insert Zone SHALL be exposed as a fixed-length slice of the configured length. It SHALL be present in every frame, including OID frames, when configured. | §4.1.3 | V |
| AOS-016 | An OID frame SHALL have VCID = 63 and a data field filled from the OID generator (CMN-020). | §4.1.4.1.5 | V |
| AOS-017 | M_PDU and B_PDU views SHALL classify their pointers (packet starts at n, no packet start, only idle data; n valid bits, all valid, only idle). A pointer that is neither one of its two reserved values nor inside its zone (a First Header Pointer ≥ the Packet Zone length in octets; a Bitstream Data Pointer ≥ the Bitstream Data Zone length in bits) SHALL be `Malformed` in both modes: it points outside the field it indexes (API-032; [open issues](../09-open-issues.md) OI-33). A Bitstream Data Pointer naming the zone's last bit SHALL be `InvalidField` (`bitstream_data_pointer`) in both modes: a zone with no idle data has the pointer all ones (§4.1.4.3.3.3), which API-031 makes a strict error and API-032 does not let lenient mode accept; the writer accepts a count of valid bits only for 1 ≤ n < the zone's bits. Rejecting the last bit is the project's reading: §4.1.4.3.3.2–3 define the pointer as the last valid bit and require all ones when the zone holds no idle data, and the Blue Book does not say that a receiver rejects the pointer that names the last bit (second review, [m2-vectors.md](../verification/reviews/m2-vectors.md), AOS finding 1). | §4.1.4.2.2, §4.1.4.3.3 | V |
| AOS-018 | A configuration in which a VC carries B_PDUs SHALL be rejected with `InvalidConfig` if its Bitstream Data Zone is longer than 2 047 octets, in both editions. The 14-bit Bitstream Data Pointer holds the index of the last valid bit and reserves all ones (`0x3FFF`, no idle data) and all ones minus one (`0x3FFE`, only idle data), so it can name every bit of a zone of at most 16 382 bits; the longest zone of whole octets within that is 2 047 octets (16 376 bits, last index `0x3FF7`). In a zone of 2 048 octets the index 16 382 would read as "only idle data". In the Issue 5 edition the configuration SHALL also be rejected if the frame length exceeds 2 048 octets (16 384 bits) while any VC carries B_PDUs, the limit 732.0-B-5 states for the Bitstream Service; the zone is then at most 2 040 octets (frame − 6-octet Primary Header − 2-octet B_PDU Header). 732.0-B-4 has the same pointer and reserved values but states no frame limit (OI-35 item 7). The frame limit of the Issue 5 edition is a project choice: 732.0-B-5 gives it in a NOTE to §4.1.4.3.3.4, not in a SHALL, and rejecting a longer frame is the project's way to keep the Bitstream Service within it (second review, AOS finding 2). | §4.1.4.3.1.3–4, §4.1.4.3.3.2–4 and note; 732.0-B-4 §4.1.4.3.3 | T |
| AOS-019 | The writer SHALL compute the FHEC (when configured) and the FECF. It SHALL accept the VC frame count, cycle, replay flag, and data field contents from the caller or engine. | §4.1.2, §4.1.6 | V |
| AOS-020 | A channel table SHALL be rejected with `InvalidConfig` naming `vc_id` when it holds no virtual channel. The valid Spacecraft IDs of the physical channel are those of its virtual channels (AOS-010), so a table without one rejected every frame, Only Idle Data frames on VCID 63 included (OI-55). | AOS-021 | A one-shot OID frame encoder (with a form for the Galois generator; C ABI `sym:aldis_aos_encode_oid`) SHALL write the frame of AOS-016 in one call: VCID 63, no OCF or SDLS fields, the Insert Zone given by the caller, the data field filled from the supplied generator, the FHEC and the FECF computed. It SHALL make the checks of the two-phase OID writer and check the Insert Zone length as `encode` does (`LengthMismatch` `insert_zone_len`). **Order of the decoder's checks (a project choice).** The Blue Book gives no order. `AosFrame::decode` reports the first failure of: the frame length (`LengthMismatch`), the FHEC (`HeaderUncorrectable`), the FECF over the corrected header (`CrcMismatch`, AOS-014), the version (`UnsupportedVersion`, AOS-011), the channel lookup (`UnknownChannel`), the data field room (`Malformed`, `frame_data_field`), the M_PDU and B_PDU pointers (`Malformed` or `InvalidField`, both modes, AOS-017), and then, in `decode` only (`decode_lenient` reports them as flags), the first deviation in header order (cycle, Issue 4 header spare, PDU spare; AOS-012, AOS-002, AOS-003). So a spare bit set with a pointer past the zone is `Malformed`, and a frame with a wrong version and a wrong FECF is `CrcMismatch`. The vectors pin the order of the pointer and the spare (`aos-i4-dec-006-s`, `-l`) and of the version against the FECF (`aos-inv-dec-009`, added after the second review, AOS finding 3).

**Insert Service on rejected frames.** 732.0 §4.3.7.4 has the All Frames Reception Function extract IN_SDUs regardless of GVCID, and permits extraction before FECF checking when error protection is not required. `AosFrame::decode` gives a view only for accepted frames. The Insert Zone occupies a fixed position in every frame of the physical channel: octets `primary_header_len` to `primary_header_len + insert_zone_len` (where `primary_header_len` is 8 with FHEC, 6 without). The link engine (M4, LNK-053) can slice the zone from the raw input of rejected frames that pass the frame length check.

**OID data.** The decoder does not check the data of an OID frame (AOS-016): 732.0-B-5 §4.1.4.1.5.2 requires the pseudo-noise sequence, but the sequence depends on the generator's position across frames (CMN-021), which a stateless decoder does not know, and receivers discard the data. `aos-iz-dec-003` and `aos-sec-dec-002` accept OID data that is not the sequence.

## 5. Anomaly flags (lenient mode)

`AosAnomaly` flags, returned by `decode_lenient` in a `Lenient` (a strict view has none, API-031). The bit index is the flag's position in `AnomalySet::bits()` and is shared with the C ABI. It never changes once `aldis-aos` is released. Before OI-33 the flags were listed without bit indices, so withdrawing `PointerBeyondZone` (an out-of-range pointer is `Malformed` in both modes, AOS-017) and `FhecCorrected` (the view reports `corrected_symbols()` in both modes, AOS-014) reserves no bit. Version, length, FHEC, and FECF errors remain errors in both modes (API-032).

| Bit | Flag | Deviation | Source |
|---|---|---|---|
| 0 | `CycleNonZeroWhileUnused` | VC Frame Count Cycle ≠ `0000` with its Use Flag = 0 (AOS-012) | §4.1.2.5.5.3 |
| 1 | `BpduSpareSet` | B_PDU Reserved Spare ≠ `00` | §4.1.4.3.2.2 |
| 2 | `Issue4SpareSet` | In `Issue4Compatible`, Primary Header bits 42–43 ≠ `00` (AOS-002) or M_PDU Reserved Spare ≠ `00000` (AOS-003) | 732.0-B-4 §4.1.2.5.4, §4.1.4.2.2 |
