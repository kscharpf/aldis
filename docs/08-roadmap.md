## 3. Language rollout

| Phase | Language | Approach |
|---|---|---|
| 1 | Rust | Reference implementation (v1); the recommended choice |
| 1 | C / C++ | C ABI over Rust (`aldis-ffi`) + header-only C++ wrapper (M5) |
| 1 | C++ (native) | Native implementation for legacy flight software that cannot easily take a Rust toolchain ([C++ profile](profiles/cpp.md)); same header (CABI-070) and C++ wrapper API (CABI-072) |
| 2 | Python | Bindings over the C ABI (or PyO3 over the Rust crates) with an idiomatic API; vectors run under pytest |
| 2 | Go | cgo bindings over the C ABI |
| 2 | Java / C# | Panama (FFM) or JNI / P/Invoke over the C ABI |
| 3 | C (native) | Full native implementation of this specification; same header (CABI-070) |

Every phase is gated on passing the shared vector suite (TV-*).

### 3.1 Native C++ alongside the Rust milestones

The native C++ implementation follows the Rust crates module by module. A C++ module starts once its Rust crate has merged, and is done when it passes the vector suite and the differential tests against the Rust crate (VER-053) and meets the [C++ profile](profiles/cpp.md). The Rust crates are never held back for the C++ port.

Differential testing calls the native library through the C ABI, so the codec part of `aldis.h` is designed with each codec's milestone rather than all at M5: the slice for a milestone's codecs is specified, generated by `aldis-ffi`, and implemented by the native C++ library in that milestone. When the M1 codecs (time, SPP, EPP) get their slice is open ([OI-21](09-open-issues.md)).
