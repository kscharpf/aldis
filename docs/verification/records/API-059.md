# Record: API-059

| | |
|---|---|
| Requirements | API-059 |
| Method | I |
| Check | Inspection of the engines of `aldis-cop1` and `aldis-link` for an output queue, 2026-11-05; the test of `file:crates/aldis-link/tests/cltu_packer.rs` that consumes actions after the next input |

An engine returns the actions of one input as an `Actions` value (`file:crates/aldis-core/src/engine.rs`): a fixed array of `N` entries and a length, `Copy`, with no pointer into the engine. The octets go to the caller's output area, which the actions name by `OutRange`.

What the inspection looked for, and found:

- `git grep -n "poll_transmit\|poll_deliver\|poll_event\|poll_timeout" crates` finds nothing: no call drains a queue of the engine (OI-56).
- The queues that the engines hold are input-side (API-052, API-060): the packet queue of the generators (`file:crates/aldis-link/src/generator.rs`, `file:crates/aldis-link/src/access.rs`), the SDU queue of the segmenter (`file:crates/aldis-link/src/segmenter.rs`), the Sent_Queue and Wait_Queue of FOP-1 (`file:crates/aldis-cop1/src/fop1.rs`), the offered field of each VC of the multiplexer (`file:crates/aldis-link/src/mux.rs`), and the unit in progress of the CLTU packer (`file:crates/aldis-link/src/cltu.rs`). Every step function builds a fresh `Actions` and returns it; none stores one in `self`.
- The test `the_actions_of_one_input_are_consumed_after_the_next_input` holds the actions of one input while the engine takes another, and reads them afterwards: it compiles only when the actions borrow nothing of the engine, and it passes only when the second input does not depend on the first actions having been consumed.

Redo the inspection in every pull request that adds an engine or a field to an engine's state.
