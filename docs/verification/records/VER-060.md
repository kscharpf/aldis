`.github/workflows/verify.yml`: `workflow_dispatch` is its only trigger and branches its only refs; it runs three stages on `ubuntu-24.04`: `prepare` (`contents: read`, `packages: write`) builds `xtask` once and passes it to the other jobs as an artifact (with the commit and the workspace path it was built at; the composite action `.github/actions/get-xtask`, used by `part` and `assemble`, is the one copy of the rule: a job uses the binary only when both match what it checked out and `xtask help` runs, and else builds `xtask` itself), decides from `cargo xtask verify list` whether the run starts a container and then makes sure the registry has the image; four `part` jobs (`contents: read`, `packages: read`; `fail-fast`) run `cargo xtask verify part <group>` and upload their `target/verify/*/` also when they fail; `assemble` (`contents: write` for the notes ref, `statuses: write`) downloads the part records outside `target/verify/<commit>` and runs `cargo xtask verify assemble --publish`, then uploads the record (VER-067); `file:xtask/src/verify/mod.rs` writes the record's `source` from the GitHub Actions environment, and `file:xtask/src/verify/publish.rs` sets the status's `target_url` to the run. The image: `verify.yml` sets `ALDIS_VERIFY_PULL=ghcr.io/kscharpf/aldis-verify`; `prepare` has `packages: write` and the parts `packages: read`; `file:xtask/src/verify/image.rs` pulls `<16 hex digits of the input hash>-<arch>` only when the image's labels `dev.aldis.verify.inputs` (the full hash) and `org.opencontainers.image.revision` match the hash it computes for the commit and the hash it recomputes from that revision's files, and its architecture is the host's, and else builds; `prepare` looks up the manifest of the reference `cargo xtask verify image --ref ghcr.io/kscharpf/aldis-verify` prints (the tag from the hash of the image inputs, from git alone), in this repository, only when `verify list` says the run starts a container (a run that needs none neither pulls nor builds one), and runs `verify image --push` to build and push the image only when the lookup answers `manifest unknown`, `no such manifest` or `not found` (any other failure of the lookup fails the job), before any part starts; each part checks the labels when it pulls the image and builds it itself when they do not hold, so a tag whose labels do not hold costs each of the four parts a local build, and nothing repairs the tag until the nightly on `main` pushes the same input hash; in another repository the parts build it; `verify image --push` (nightly) and `--push-image` push a built image only under GitHub Actions, after the workflow's `docker login` with `GITHUB_TOKEN`, guarded by `github.repository == 'kscharpf/aldis'`; the record's `image.source` is `built` or `pulled` with the reference, digest, and revision (test in `file:xtask/src/verify/image.rs` for the tag and the recomputed hash). Cancelling (VER-060, last sentences): no workflow step cancels a run for `main` moving. The two cancels are both requested: the `concurrency` group of `verify.yml` (`verify-${{ github.ref }}`, `cancel-in-progress: true`) replaces the in-flight run of a ref when a newer run of the same ref is dispatched, which only a contributor's or `scripts/reverify`'s dispatch does; and `scripts/reverify --cancel <n>` (`cancel_inflight`): it lists the runs of `verify.yml` for the pull request's own branch, keeps those of the head commit (`origin/<branch>`) that are not completed, and cancels them only when `git merge-base --is-ancestor origin/main <head>` exits 1; the pull request must be open; it runs before the locks and again once they are held, and implies `--wait`. A cancelled run is reported by `scripts/reverify` as `cancelled`, kept as the PR's last line (`--status`, exit 1), and not retried. `scripts/test-reverify` covers: no cancel without the flag; the PR's own run is cancelled and no other PR's or older head's; a current head is left alone; `--status --cancel` is a usage error; a cancelled run is neither FAILED nor STALE and is not retried; `--cancel` ends a reverify that was watching the run and then dispatches a new one. Reviewed in each PR that touches `scripts/reverify` or the cancel settings of `verify.yml`.
