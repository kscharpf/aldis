The constructors of the physical channel, the VC, the MAP, and `TruncatedFrameLen` are `const fn` |

The tables `VcTable` (TC, AOS, USLP) and the TM master channel's `with_vc` build their arrays by a validation that loops, so they are constructed at run time and cannot be a `const` or `static`; they are values that clone, compare, and print, and a mission that wants them in read-only memory builds them once at start-up. The four configuration-contract integration tests check the property by what a test can observe: each type satisfies `Copy`/`Clone + PartialEq + Debug + Send + Sync + 'static` (a type with a borrowed field would not be `'static` generically), and the TC and USLP physical channels, VCs, and MAPs fill a `static`.

One thing the review found is closed, and one it leaves open, for the maintainer through the coordinator:

1. Closed (`m2/hazard-controls`): The constructor and accessor of the truncated frame length (`file:crates/aldis-uslp/src/config.rs`) are `const fn`, since the check (a range of 6 to 32) is const-evaluable, and `file:crates/aldis-uslp/tests/config_contract.rs` builds a `VcConfig` with a truncated frame length in a `static` (`TRUNCATED_VC`). The change is not breaking.
2. Open: `VcParams` has public fields (`file:crates/aldis-uslp/src/config.rs`, the struct after `TruncatedFrameLen`), against the wording of RS-012 ("private fields"). It is the record of the parameters that the VC constructor validates, and the parameter accessor returns a copy, so a changed copy does not change the VC (`test:crates/aldis-uslp/tests/config_contract.rs::a_configuration_cannot_change_after_construction`); but the type is a configuration that can hold a value the VC constructor would reject.
