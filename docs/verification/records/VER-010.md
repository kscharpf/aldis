Verify checks `exerciser-<target>`, and the nightly CI job `exerciser`: `exerciser/` calls every public `aldis-core` API with the core vectors (`exerciser/src/exercise.rs`, and `ocf.rs` for the OCF, M2 WP-1), every public `aldis-time`, `aldis-spp` (with `time`), and `aldis-epp` API (`exerciser/src/time.rs`, `spp.rs`, `epp.rs`), every public `aldis-aos` API (`exerciser/src/aos.rs`, M2 D16; the FHEC since WP-4 module 1, the frame codec since modules 2–7), every public `aldis-tm` API (`exerciser/src/tm.rs`, M2 WP-2), every public `aldis-tc` API (`exerciser/src/tc.rs`, M2 WP-3), and every public `aldis-uslp` API (`exerciser/src/uslp.rs`, M2 WP-5). It also runs every live case of `test-vectors/{time,spp,epp,aos,tm,tc,uslp}/`, which `exerciser/build.rs` embeds, and compares every output exactly, as the host suites do (`exerciser/src/vectors.rs`, TV-012). Inputs pass through `black_box`. The calls were checked complete on 2026-10-19 (M1 WP-5) against the symbols an unoptimized exerciser build references. Since M2 WP-0c it also calls every function `aldis-ffi` exports (`exerciser/src/ffi.rs`, M2 plan D16; the `aldis_tm_*` functions since M2 WP-2 module 7: 1379 cases, 0 failed, 1 not representable on thumbv7em under QEMU, 2026-10-23), with the panic handler of `aldis-ffi`'s feature `panic-unreachable`, so the link check covers the C ABI. The release build (LTO, `panic = "abort"`) links with a panic handler that calls the undefined `aldis_panic_is_unreachable` on thumbv7em, armv7r, and riscv32imac. The `inject-panic` canary must fail to link with that symbol, so the check cannot pass vacuously. The exerciser then runs under QEMU 8.2 on every target and exits through semihosting with failure if any case fails or any exception or trap occurs (M1 D6): Cortex-M4 on `mps2-an386`, Cortex-R5F on the `none` machine (`mps3-an536`, Cortex-R52, needs QEMU ≥ 9.0), and RV32 on `virt`. `epp-idle-009`, a total length of 2^32, does not fit a 32-bit `usize`; the run reports it as not representable. The non-gating check `rust-sparc-leon3` (OI-08) does the same on LEON3: the link check and canary with `-C target-cpu=leon3`, `core` built by `-Z build-std=core` on the tooling nightly, and GNU ld (`exerciser/link-leon3.x`), then the vector run under QEMU 8.2 `leon3_generic`, where the exerciser writes to the APBUART and exits through error mode (`ta 0` on success, QEMU exits with 0; any other trap aborts QEMU); first run 2026-10-21: 993 cases, 0 failed, 1 not representable. With `aldis-tm` (2026-10-23, M2 WP-2, thumbv7em under QEMU): 1142 cases, 0 failed, 1 not representable; the link check first found the length-check panic of `copy_from_slice` reachable from `aldis_tm::encode`, which was removed. With `aldis-uslp` (2026-10-23, M2 WP-5, thumbv7em under QEMU): 1917 cases, 0 failed, 1 not representable; the link check passed on the first build. With the `aldis-aos` frame codec (2026-10-23, M2 WP-4, branch `m2/aos-codec`, thumbv7em, armv7r, and riscv32imac under QEMU): 1564 cases, 0 failed, 1 not representable; after the merge with `aldis-uslp` (2026-10-24, the same three targets): 2141 cases, 0 failed, 1 not representable. With the `aldis_aos_*` functions and `AosFrameWriter::resume` (2026-10-24, M2 WP-4 module 8, branch `m2/aos-c-abi` merged with `m2/rs020-check`, thumbv7em under QEMU): 2163 cases, 0 failed, 1 not representable; the link check passed on the first build. `cargo xtask consistency` fails when a gated crate is not an exerciser dependency, has no vector group in `exerciser/build.rs`, or a vector file of an exercised crate is not embedded.

TC C ABI (M2 WP-3 module 8, branch `m2/tc-c-abi`, 2026-10-24): `exerciser/src/ffi.rs` calls every `aldis_tc_*` and `aldis_clcw_*` function, and `exerciser/src/tc.rs` the new `TcFrame::peek_header` and `TcFrameWriter::resume`; the link check passed on the first build, and the run on thumbv7em under QEMU gave 2162 cases, 0 failed, 1 not representable.
