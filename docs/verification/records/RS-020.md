# Record: RS-020

| | |
|---|---|
| Requirements | RS-020 |
| Method | A, I |
| Check | Review of each PR that adds or changes a public type; `cargo xtask rs020` |

Reviewed in each PR that adds or changes a public type. Audit of `aldis-core`, `aldis-epp`, and `aldis-time` on 2026-10-19: the CCS and CDS value types were brought into line in PR #21, and the remaining violations and gaps listed in [issue #22](https://github.com/kscharpf/aldis/issues/22) (`FrameCtx`, `FrameLayout`, `SecuredFields`, `EncapsulationFields`, the EPP sender-side check, `TimeCodeId`, `TimeCode::Unknown`, `Cuc::from_seconds_nanos`, the `Anomaly` trait) in the PR closing it.

Since 2026-10-24 (M2 WP-7, branch `m2/rs020-check`), `cargo xtask rs020` (`xtask/src/rs020.rs`; part of `cargo xtask ci` and the verify check `spec`) also checks one pattern mechanically: in the public API of the codec crates (`aldis-core`, `-time`, `-spp`, `-epp`, `-tm`, `-tc`, `-aos`, `-uslp`), every enum variant whose payload includes a bare integer and every `pub` field of a public type that is one is a problem unless [`xtask/rs020-exemptions.toml`](../../../xtask/rs020-exemptions.toml) exempts it with a reason; an exemption without a reason, or that matches no item, is a problem too. Its first run found 21 bare integers: three were gaps and became types (`aldis_aos::PacketOffset`, `aldis_uslp::TfdzOffset` for both pointers), and 18 are exempted. One of those, `aldis_tm::header::PacketPointer::StartsAt`, is a gap whose fix waits for a maintainer decision, because the C ABI maps it. The check reads the source textually, so a type that a macro invocation builds is checked only where the `macro_rules!` body defines it; review covers the rest of RS-020.
