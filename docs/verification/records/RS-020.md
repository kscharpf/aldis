# Record: RS-020

| | |
|---|---|
| Requirements | RS-020 |
| Method | A, I |
| Check | Review of each PR that adds or changes a public type; `cargo xtask rs020`; `cargo xtask restricted` |

Reviewed in each PR that adds or changes a public type. Audit of `aldis-core`, `aldis-epp`, and `aldis-time` on 2026-10-19: the CCS and CDS value types were brought into line in PR #21, and the remaining violations and gaps listed in [issue #22](https://github.com/kscharpf/aldis/issues/22) (`FrameCtx`, `FrameLayout`, `SecuredFields`, `EncapsulationFields`, the EPP sender-side check, `TimeCodeId`, the unknown time code, the CUC constructor from seconds and nanoseconds, the `Anomaly` trait) in the PR closing it.

Since 2026-10-24 (M2 WP-7, branch `m2/rs020-check`), `cargo xtask rs020` (`file:xtask/src/rs020.rs`; part of `cargo xtask ci` and the verify check `spec`) also checks one pattern mechanically: in the public API of the codec crates (`aldis-core`, `-time`, `-spp`, `-epp`, `-tm`, `-tc`, `-aos`, `-uslp`), every enum variant whose payload includes a bare integer and every `pub` field of a public type that is one is a problem unless [`file:xtask/rs020-exemptions.toml`](../../../xtask/rs020-exemptions.toml) exempts it with a reason; an exemption without a reason, or that matches no item, is a problem too. Its first run found 21 bare integers: four were gaps and became types (the packet offsets of `aldis-aos` and `aldis-tm`, and the TFDZ offset of `aldis-uslp` for both pointers), and 17 are exempted. The C ABI still takes the TM packet offset as a `uint16_t`; an offset above `0x7FD` fails with the error and detail the writer gave before, at the same point (`file:crates/aldis-ffi/tests/tm.rs`, `packet_offsets_above_0x7fd_fail_as_the_writer_checks_them`, which passes on the code before the change too). The check reads the source textually, so a type that a macro invocation builds is checked only where the `macro_rules!` body defines it; review covers the rest of RS-020.

Since 2026-10-24 (M2 WP-7, branch `m2/wp7-tests`), `cargo xtask restricted` (`file:xtask/src/restricted.rs`; part of `cargo xtask ci` and the verify check `spec`) checks that every *restricted type* of the same crates has a test: a public struct or enum with a checked constructor, an inherent `pub fn` that returns `Option<Self>` or `Result<Self…>` and takes its arguments by value, or is named `new` or `try_new` and takes no reference but to a slice, or a `TryFrom` impl (a type a `macro_rules!` body defines counts once per invocation). A test of the crate (its `restricted` integration test) names each one in a `// restricted: <Type>` marker; a type without a marker, or a marker that names no restricted type, is a problem. Each such test shows that the constructor accepts exactly the range the cited clause or requirement gives (exhaustively over every `u8`, `u16`, and `bool` input; at the edges and with a proptest for wider inputs), rejects every other value with the documented error, and that every accepted value survives its wire field. `cargo xtask restricted list` prints the types it finds. Any other constructor that takes a reference (a frame writer's `begin`, the segmenter constructor over a configuration) or that decodes (`decode…`, `parse…`) does not make a type restricted in this sense; the codecs' property tests cover those. The slice rule was added after the review of #116, which found the P-field tail constructor untested; it also brought in `Agency` and the three `VcTable`s.

Since 2026-11-19 (branch `feat/rs020-engines`), `cargo xtask rs020` also reads the engine crates `aldis-link`, `aldis-cop1`, and `aldis-sync` (11 crates; Layers 0–2), with the same exemption list. The fields that gave the engines their types came first: #669 typed the Virtual Channel, MAP, and pointer fields of the `aldis-link` data units (the protocol's VC and MAP types, `FirstHeaderPointer`, `AosPointer`, `LastValidOctet`, `BitstreamPointer`; #672 is the reference application's companion), and #683 typed `Fop1Config.sliding_window_k` and the two repetitions of `aldis-cop1` as `NonZeroU8` (#684 is the companion). The first run on the three crates found 22 bare integers (21 in `aldis-link`, 1 in `aldis-cop1`, none in `aldis-sync`) and 40 in all. Twenty-one are exempted with a reason: the octets a `Reconfigure` discarded (eight outputs), the counts and bit counts an engine reports (`DataUnit.frames`, the two `Packets.count`, `DataField.bit_count`, `FrameGap.missing`), `SubmitBits.bit_len`, `StartsAt.0`, `FrameFields.frame_len`, and the VCF Count fields of the multiplexer, whose only bound is a relation to a configuration, a slice, or a zone that the engine checks, or which are full-width counts that the header masks. One, `IncompletePacket.pvn`, is a gap: `PacketVersion` of `aldis-core` types it, and it is exempted as a gap, [issue #688](https://github.com/kscharpf/aldis/issues/688), until that type replaces it. `Transmit.repetitions` is exempted as pending #682 (0 for a Type-BD frame until the clause is settled) and the exemption goes when #682 types it. `cargo xtask restricted` keeps the eight codec crates (maintainer decision Q3, 2026-11-17): an engine's checked constructor is `new(config)`, and the range it accepts is the configuration's, already a restricted type of a codec crate.
