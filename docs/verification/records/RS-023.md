# Record: RS-023

| | |
|---|---|
| Requirements | RS-023 |
| Method | I |
| Check | Review of the writer typestate and of the receiving types; `cargo xtask trace` for the tests that name RS-023 |

The sending half of RS-023 is implemented by the finishing states `Unprotected`, `Protected`, and `Finalized` of `file:crates/aldis-core/src/finishing.rs` and by the codec writers `TmFrameWriter`, `TcFrameWriter`, `AosFrameWriter`, and `UslpFrameWriter` (`file:crates/aldis-tm/src/writer.rs`, `file:crates/aldis-tc/src/writer.rs`, `file:crates/aldis-aos/src/writer.rs`, `file:crates/aldis-uslp/src/writer.rs`), each generic over a `FrameState`. `begin` returns the writer `Unprotected`, where the fields are filled; `protect(hook, ctx)` applies a `SecurityHook`, and `unsecured()` takes the `NoSecurity` path of a channel with no Security Header or Trailer (it fails otherwise); both consume the writer and return it `Protected`; `finalize()` consumes that and computes the FHEC (AOS) and the FECF last. Only the `Finalized` writer has `octets`, `into_octets`, and `len`. For TC and USLP, whose Security Trailer, Frame Length, and OCF depend on the User Data or TFDZ length, `protect` and `unsecured` take that length, so the hook sees final ranges. The AOS writer leaves the FHEC octets zero until `finalize` (asserted by `unfinished_frame_is_defined` and by `protect_runs_before_the_fhec_and_the_fecf` in `file:crates/aldis-aos/src/writer.rs`). The mandatory `layout` method of `SecurityHook` (no default) names the Security Header and Trailer lengths a hook is for, an exact layout or the any-layout variant; `protect` rejects a hook whose layout differs from the channel's with `InvalidField`, so `NoSecurity` (layout 0/0) cannot be applied to a channel with SDLS fields, and the guard of `unsecured` holds on both entries. Tests that fill the Security fields by hand use the test-only `PreFilledSecurity` (feature `test-hooks`, the any-layout variant). On TC and USLP only, a failed hook leaves the unfinished header (TFVN or version `11`) in the buffer again (on TM and AOS the header is final from `begin`, so a failed hook leaves a frame with a final header that the caller must not transmit), and `finalize` returns `InternalError` instead of assuming that the frame slice and the CRC succeed. Each writer module has a test that applies a hook which asserts that the FECF (and the FHEC) is not yet computed when it runs, one that `NoSecurity` is rejected on an SDLS channel, one that a failing hook gives no frame, and one that `unsecured` fails on a channel with SDLS fields. An operation out of order has no method on the state it is called in, so it does not compile; the one-shot `encode` functions take the Security Header and Trailer as given and are unchanged.

The receiving half of RS-023 (`Received` → decoded view → `Plain<F>`, with `Checked<F>` beside them) is implemented in the codecs as types, not as marker parameters (maintainer decision of 2026-10-30; API-015, API-016), so that what a decoder checked is part of the type it returns:

- `Received` is the octets. A decode that fails returns no view.
- The decoded view is what the default decode returns: `TmFrame` (FECF verified before any field is read, TM-005), `AosFrame` (FHEC corrected, FECF verified), `TcFrame`, `UslpFrame`, `SpacePacket`, and `EncapsulationPacket` for the checks their decoders make. A decode that omits a check returns another type: `decode_unchecked` of `TmFrame` returns `UncheckedTmFrame` (`file:crates/aldis-tm/src/view.rs`), which offers the read accessors and no operation that takes a checked frame, and becomes a `TmFrame` only through `check_fecf`. The checked frame converts into the unchecked type with `From`, which forgets the check; the other direction does not exist.
- A frame that also matches its channel's configuration is the refined `Checked<F>` (`file:crates/aldis-core/src/checked.rs`) for `AosFrame` (`file:crates/aldis-aos/src/checked.rs`), `TmFrame` (`file:crates/aldis-tm/src/checked.rs`), `TcFrame`, and `UslpFrame`, and `ValidatedEncapsulationPacket`; `check` takes the decoded view and `check_frame` the octets of one frame; both return the refined type, and none returns `Result<()>`. The FARM-1 frame constructor `from_tc` takes `Checked<TcFrame>`. `Checked` has no public constructor, and `Check` and `CheckBytes` have no type parameter, so a frame type has one implementation that only the codec's crate can write (the orphan rule, E0117), so an outside crate cannot make a `Checked` codec frame without the codec's check (a compile-fail doc test on the `Check` implementation for `TmFrame`, `file:crates/aldis-tm/src/checked.rs`, implements the trait for `TmFrame` with a lookup type of the outside crate and is refused with E0117).
- Strict and lenient decoding are separate entry points (API-030): a strict view carries no `AnomalySet`, and a lenient decode returns the view in `Lenient` (`file:crates/aldis-core/src/mode.rs`).
- `Plain<F>` (SDLS verified, or no SDLS; `file:crates/aldis-core/src/plain.rs`) is generic over the frame, orthogonal to `Checked<F>` and `Lenient`, and `Plain<Checked<F>>` carries both. A decoded view or a `Checked<F>` becomes `Plain` only through `into_plain(NoSecurity)`, a provided method of `SecuritySlices`, which each codec implements for its frame (`TmFrame`, `TcFrame`, `AosFrame`, `UslpFrame`; `file:crates/aldis-tm/src/security.rs` and the sibling files) and which fails with `InvalidField` for a frame that has a Security Header or Trailer. `Plain` has no public constructor, and `SecuritySlices` has no type parameter, so only the codec's crate can implement it for its frame (the orphan rule, E0117; a compile-fail doc test on the `TmFrame` implementation implements it from outside and is refused); the SDLS `verify` step for a channel with SDLS (API-074) is not provided for the engine input (issue #230). The decoders of AOS, TC, and USLP decode a frame of a channel the lookup does not hold (API-017), and the check of each codec rejects it (`check` of TM and AOS, `check_frame` of TC and USLP). The `FrameReceiver` input `Frame` takes the `Plain` type of its protocol (the associated type `Plain` of `ReceiveProtocol`, `file:crates/aldis-link/src/receiver.rs`), the only way in; `CheckedFrame` and its constructor on the caller's word no longer exist. Calling the steps out of order does not compile: a decoded view has no path to the engine input but `into_plain`.

Tests name API-015 and API-016 with the requirement of the check they cover: `file:crates/aldis-tm/src/view.rs` (`length_and_fecf_are_checked_first`: the unchecked frame fails `check_fecf` on a bad FECF and equals the checked decode on a good one) and `file:crates/aldis-tm/src/checked.rs` (the checked frame).
