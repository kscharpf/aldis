# Record: VER-011

| | |
|---|---|
| Requirements | VER-011 |
| Method | A |
| Check | Verify check `stack`: `cargo xtask stack`; `nightly.yml` job `stack-sizes` |

Verify check `stack` (since 2026-10-24, M2 WP-7, branch `m2/wp7-checks`; `file:xtask/src/stack.rs`): `cargo xtask stack` makes two builds for each of thumbv7em, armv7r, and riscv32imac on the tooling nightly, with `core` and `compiler_builtins` built from source (`-Z build-std=core`) and `-Z emit-stack-sizes --emit=llvm-ir,link`: `ffi`, the `aldis-ffi` static library as it ships (`--no-default-features --features panic-handler --release`; the release profile's LTO does not apply to `aldis-ffi`, whose crate types include `rlib`, so the archive holds one object per crate), and `exerciser`, the exerciser, which calls every public function with real capacities, without LTO and with its own crate in 256 codegen units and without MIR inlining, so that the generic functions it instantiates stay functions of their own. From the objects it takes each function's frame (`.stack_sizes`) and the call graph (the relocations of each function: calls, tail calls, and addresses taken), and checks the graph complete against the LLVM IR of the same compilations (only the IR files that the build's own compilations wrote): a reachable function with an indirect call (`dyn`, a function pointer), inline assembly, a dynamic stack allocation, no frame, or no IR, a call that no object defines, and a cycle (GEN-022) each fail, unless `file:xtask/stack-budgets.toml` exempts the function with a stated bound. An `indirect` exemption accepts only the named function's own indirect calls, never inline assembly or its callees'. The walk stops at a diverging function of `core` (the panic machinery), counting its frame: GEN-020 forbids panics and VER-010 proves that none survives the release link. The entry points are the aldis_* functions of the C ABI and every function whose demangled path names a public function of a library crate, by the item's Rust visibility read from the source (`file:xtask/src/api.rs`), wherever it is emitted, monomorphisations included; `pub(crate)` helpers are not entry points. An entry point measured in both builds takes the larger worst case. Its worst case, its frame plus the deepest chain of callee frames, must stay within its target's budget for its kind (`rust`, `c-abi`) in `file:xtask/stack-budgets.toml`: rust = 4096 and c-abi = 10240 bytes on every target (maintainer, 2026-10-24, #113; rust raised from 1024 once the table constructors were measured, OI-45). The bound leaves out interrupts and the caller's frames. The check's inputs are `RUN` (which holds `xtask/`, the budgets file, and `tooling-nightly`), `crates/**`, `exerciser/**`, and `test-vectors/**` (which the exerciser's build script embeds); it takes about 35 s per target on a warm macOS host.

The published table is the report of the same run, `target/spec/stack-<target>.md`: every entry point with its worst case, build, and deepest path, the exemptions applied, the panic paths where the walk stopped, the public functions measured in neither build (inlined into every caller, so that their stack is in the callers' frames, or never instantiated: 427 on each target on 2026-10-25, accessors and `const fn` constructors), and the frame of every function reached. The nightly job `stack-sizes` runs `cargo xtask stack <target>` for each target and keeps the report as the artefact `stack-sizes-<target>`, also when a budget fails; the release takes it from the nightly run of the release commit.

Exemptions: `indirect = 0` for the core::fmt functions that call the caller's core::fmt::Write, or the `Debug` of a set's entries, through a `dyn` reference (core::fmt::write, Formatter::pad, `pad_integral`, its `write_prefix`, `padding`, `debug_set`, DebugSet::finish, DebugInner::entry), reached from the `Display` of the core error type and the `Debug` of `AnomalySet` (the writer and the entries are the caller's, maintainer 2026-10-24); `frame = 24` for `__aeabi_uldivmod` on the two ARM targets, assembly in `compiler_builtins` with a frame read from its disassembly.

Measured 2026-10-25 (`nightly-2026-10-15`, `m2/wp7-checks`), 558 Rust and 113 C ABI entry points per target, about 940 functions reached, no indirect call or recursion outside the exemptions; one panic path, core::slice::copy_from_slice_impl::len_mismatch_fail, in the `exerciser` build only:

Over the `rust` budget on 2026-10-25, so that the check fails until the maintainer decides: on every target, the channel table constructor of `aldis-tc` (`<64, 64>`), `aldis-aos` (`<64>`), and `aldis-uslp` (`<16, 32>`), whose frames hold the table they return (3408, 1328, and 1344 bytes on thumbv7em); on the two ARM targets also the AOS frame encoder for tables of 2, 8, and 64 channels and the USLP frame decoder for tables `<2, 2>` and `<16, 32>`, by 32 to 72 bytes. The earlier measurement of 2026-10-24 (largest Rust entry point 752 bytes) missed them: it took only global symbols as Rust entry points, so every monomorphisation of a generic function was left out (review of #113).

Most of the C ABI's stack is the channel table that the TC, AOS, TM, and USLP functions build on the stack from the caller's array (`master_channel_at`, `table_at`): 4768 of the 8576 bytes of the since-removed TC validation function on thumbv7em. Decided at the M2 exit review (maintainer, 2026-10-26, chat, OI-45 option (d)): keep the current channel-table design, confirm the 4 096-byte (Rust) and 10 240-byte (C ABI) budgets, and document the stack requirements.

Before 2026-10-24, `cargo xtask stack-sizes <target>` (replaced by `cargo xtask stack`) published the per-function frames of the exerciser after LTO. First measurement (thumbv7em, 2026-10-16): 19 functions after LTO, largest frame 552 bytes (`_start`, which inlines the vector loops). With the AOS FHEC (thumbv7em, 2026-10-20, M2 WP-4): the AOS FHEC decoder 92 bytes, `encode` 52, `write` 24.
